# Resource Indicator Part 2 — Admin API: four keys, merge semantics, association restriction

Spec: [docs/specs/api-resource.md — Admin API](../../specs/api-resource.md#admin-api), [— Which clients may be associated](../../specs/api-resource.md#which-clients-may-be-associated).

Depends on Part 1 (`model.AccessPolicy` has four fields).

## 1. Goal / Scope

In scope:

- `AccessPolicy` and `AccessPolicyInput` gain the three new fields.
- `AccessPolicyInput` switches from **replace** to **merge**, which is what the spec requires for a client that owns more than one key.
- `addResourceToClientID` rejects a client that cannot use `client_credentials`.

Out of scope: the OAuth endpoints (Part 3). After this part an admin can set all four keys and read them back; nothing enforces three of them yet.

## 2. `AccessPolicy` — four output fields

`pkg/admin/graphql/access_policy.go`. Four `graphql.NewNonNull(graphql.Boolean)` fields. The `Description` on each is the published schema, so take the wording from the spec's SDL rather than paraphrasing it — the two must not drift, and `review-pr` treats a `Description` that misstates who a permission covers as a bug.

Two descriptions in particular have to stay precise, because the obvious shorter phrasing is wrong in each case:

- `allowStaticFirstPartyClientAccess` covers `spa`, `traditional_webapp`, `native` and `confidential` declared in `authgear.yaml`. It does **not** cover `m2m` (Part 1 §4.1), and it has no effect on the `client_credentials` grant. Both exclusions belong in the text; "any first-party client" is wrong on both counts.
- `allowDynamicThirdPartyClientAccess` never covers a static `third_party_app`. The existing description already says this; keep it.

Update the two `"accessPolicy"` field descriptions that point at this type (`pkg/admin/graphql/resource.go:41`, `pkg/admin/graphql/scope.go:48`). Both currently say "governing third-party client access", which stops being true in this part — they govern every category.

## 3. `AccessPolicyInput` — merge, not replace

### 3.1 Why replace has to go

`decodeAccessPolicyInput` (`pkg/admin/graphql/access_policy.go:31-43`) returns a `*model.AccessPolicy` in which an omitted GraphQL field is the Go zero value, i.e. `false`. The store then writes the whole object (`store_resource.go:87-93`, `store_scope.go:95-101`). With one key that is indistinguishable from merging. With four it means a caller that sets one key clears the other three — and the portal is exactly such a caller today (`DynamicClientsAccessRow.tsx:31-42` sends `allowDynamicThirdPartyClientAccess` alone).

So the merge switch and the three new keys belong together, and land in one commit. There is no deployment ordering constraint between them — the PR squash-merges, so the state where a four-key input still replaces never ships.

### 3.2 `model.AccessPolicyPatch`

`pkg/api/model/access_policy.go` (created in Part 1):

```go
// AccessPolicyPatch is a partial AccessPolicy. A nil field is left unchanged
// by an update, and defaults to false on create.
type AccessPolicyPatch struct {
	AllowStaticFirstPartyClientAccess  *bool `json:"allow_static_first_party_client_access,omitempty"`
	AllowStaticThirdPartyClientAccess  *bool `json:"allow_static_third_party_client_access,omitempty"`
	AllowDynamicFirstPartyClientAccess *bool `json:"allow_dynamic_first_party_client_access,omitempty"`
	AllowDynamicThirdPartyClientAccess *bool `json:"allow_dynamic_third_party_client_access,omitempty"`
}
```

The `json` tags must match `AccessPolicy`'s, since §3.4 merges the marshalled patch straight into the stored object. Assert that in the same test that already pins the tags (Part 1 §5).

`decodeAccessPolicyInput` returns `*model.AccessPolicyPatch`, setting a field only when the GraphQL key is present:

```go
if v, ok := m["allowStaticFirstPartyClientAccess"].(bool); ok {
	patch.AllowStaticFirstPartyClientAccess = &v
}
```

Keep the existing outer behaviour: `accessPolicy` absent or explicitly `null` returns `nil`, meaning "unchanged on update, all-false on create". That distinction is what `UpdateResourceOptions.AccessPolicy == nil` already keys off.

`NewResourceOptions.AccessPolicy`, `UpdateResourceOptions.AccessPolicy` and their `Scope` equivalents (`pkg/lib/resourcescope/resource.go:36,44`, `scope.go:29,38`) change type from `*model.AccessPolicy` to `*model.AccessPolicyPatch`. The four call sites in `pkg/admin/graphql/{resource,scope}_mutation.go` (lines 82, 155, 97, 176) need no edit beyond the type flowing through.

### 3.3 Create

`Store.NewResource` (`store_resource.go:20-33`) and `NewScope` build the initial `model.AccessPolicy` from the patch — a nil pointer field stays `false`, which is the documented create default. A small shared helper on the patch keeps the two in step:

```go
func (p *AccessPolicyPatch) Apply(base AccessPolicy) AccessPolicy
```

with a nil receiver returning `base` unchanged. `NewResource`/`NewScope` call `options.AccessPolicy.Apply(model.AccessPolicy{})`.

### 3.4 Update — merge in the database, not in Go

`Store.UpdateResource` and `Store.UpdateScope`:

```go
if options.AccessPolicy != nil {
	patch, err := json.Marshal(*options.AccessPolicy)
	if err != nil {
		return err
	}
	// Merge rather than replace: `||` on two jsonb objects takes the
	// right-hand value for a shared key and keeps every other key on the
	// left, which is exactly AccessPolicyInput's contract. Doing it in SQL
	// rather than read-modify-write keeps a concurrent update of a
	// different key from being lost.
	q = q.Set("access_policy", squirrel.Expr("access_policy || ?::jsonb", patch))
}
```

Verified against `Masterminds/squirrel@v1.5.4`: `UpdateBuilder.Set` type-asserts its value to `Sqlizer` and splices the expression's SQL and args in place (`update.go:84-98`), so this renders `access_policy = access_policy || ?::jsonb` with the argument ordered ahead of the `WHERE` args. The column is `jsonb NOT NULL DEFAULT '{}'`, so the left operand is never `NULL` and the `||` never collapses the row to `NULL`.

Because `AccessPolicyPatch` uses `omitempty` on pointer fields, an unset field marshals away entirely and a field set to `false` marshals as `"key": false` — which is what makes clearing a key work. This is the one place `omitempty`-on-a-pointer versus `omitempty`-on-a-bool actually matters; a `*bool` was chosen for exactly that.

### 3.5 `accessPolicy: {}` stops clearing the policy

Worth stating only because the current behaviour is not the obvious one. `accessPolicy: {}` clears every key today: `graphql-go` coerces an input object with no fields to a non-nil empty map (`values.go:151-167`), which is not nullish (`values.go:299-322`), so `decodeAccessPolicyInput` returns an all-`false` policy and the store replaces with it.

After the switch it is a no-op, which is what an empty patch should mean. Treat this as part of the fix rather than as a separate consequence — no entry anywhere, no migration note. Cover it with the unit test in §7 so it does not drift back.

## 4. Restricting who can be associated

The spec: *"Only a client whose application type permits the `client_credentials` grant may be associated with a Resource. The Admin API rejects an attempt to associate any other client, separately from the error it already returns for a client ID that does not exist."*

`Commands.AddResourceToClientID` (`pkg/lib/resourcescope/commands.go:66-76`) checks only that the client ID resolves. Add the type check right after:

```go
var ErrClientCannotBeAssociatedWithResource = apierrors.Invalid.
	WithReason("ClientCannotBeAssociatedWithResource").
	New("client cannot use the client_credentials grant")
```

```go
client, found := c.OAuthConfig.GetClient(clientID)
if !found {
	return ErrClientNotFound
}
if !client.ApplicationType.IsClientCredentialsFlowAllowed() {
	return ErrClientCannotBeAssociatedWithResource
}
```

`IsClientCredentialsFlowAllowed` (`pkg/lib/config/oauth.go:102-116`) is already the authority `oauth.GetAllowedGrantTypes` uses, and it is `true` for exactly `confidential` and `m2m`. Deriving the restriction from it rather than from a fresh list of application types is what keeps the two from drifting if a type is added.

**Only `AddResourceToClientID` gets the gate.** `RemoveResourceFromClientID`, `AddScopesToClientID`, `RemoveScopesFromClientID` and `ReplaceScopesOfClientID` stay as they are:

- Removal must keep working, or an admin could not clean up an association the old code let them create.
- The three scope mutations already require the resource association to exist (`checkResourceAssociatedToClient`, `commands.go:134-140`), so they cannot bring a new one into being. Gating them too would strand a pre-existing association as uneditable, contradicting "Associations of this shape that already exist are not removed".

That is the whole of the spec's "only new ones are rejected": no migration, no cleanup job, no portal warning in this part.

## 5. Schema regeneration

`make export-schemas` in the same commit as the GraphQL change — it rewrites `pkg/admin/graphql/schema.graphql`, `portal/src/graphql/adminapi/schema.graphql` and the portal `*.generated.ts`. Do not hand-edit any of them.

The portal keeps compiling across this part: `globalTypes.generated.ts` gains three optional input fields and three non-optional output fields, and no existing portal query selects `accessPolicy` by spreading it. Confirm with `cd portal && npm run typecheck` rather than assuming — the generated `Resource` type is used structurally in several components.

## 6. No `docs/BREAKING-CHANGES.md` entry

Neither change here can stop something that works today.

The association restriction (§4) refuses a call that never had an effect: `authorization_code` and `refresh_token` never consult an association, so associating a `spa` or `native` client produced a row and nothing else. Refusing it is stricter validation of a request that was already a no-op, not of a working configuration, and existing rows are untouched.

`accessPolicy: {}` (§3.5) moves from clearing to no-op — toward what the input means, not away from it.

That file is for an upgrade breaking a deployment, and it is not a changelog. Both changes belong in the PR description instead.

## 7. Test plan

- `pkg/admin/graphql/access_policy_test.go` (new) — `decodeAccessPolicyInput`: `accessPolicy` absent → nil; explicit `null` → nil; `{}` → a non-nil patch with four nil fields, which is §3.5's no-op; one key present → only that field non-nil; a key present as `false` → a non-nil pointer to `false` (the case §3.4 depends on).
- `pkg/api/model` (extend Part 1's test) — `AccessPolicyPatch`'s tags equal `AccessPolicy`'s; `Apply` over a non-zero base leaves unset fields alone and overwrites set ones in both directions.
- `pkg/lib/resourcescope` store tests — update a Resource that has `allow_dynamic_third_party_client_access: true` with a patch setting only `allow_static_first_party_client_access: true`, and assert **both** are true afterwards. This is the single assertion the whole merge switch exists for; without it the regression is invisible until a caller sets one key expecting the others to survive.
- `pkg/lib/resourcescope/commands_test.go` — `AddResourceToClientID` for `confidential` and `m2m` succeeds; for `spa`, `native`, `traditional_webapp`, `third_party_app` returns `ErrClientCannotBeAssociatedWithResource`; for an unknown client ID still returns `ErrClientNotFound` (the two must stay distinguishable, per the spec).
- `e2e/tests/resource_scope/` — extend `update_resource.test.yaml` and `update_scope.test.yaml` with a two-step merge assertion, and add a case to `add_resource_to_client.test.yaml` for the refused client type. The fixtures in that directory already declare clients of several application types.
