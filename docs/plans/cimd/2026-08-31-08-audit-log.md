# CIMD Part 8 — Audit Log Events

Spec: [docs/specs/cimd.md](../../specs/cimd.md), [docs/specs/event.md](../../specs/event.md), [docs/specs/audit-log.md](../../specs/audit-log.md).

Depends on [Part 3](2026-08-28-03-authorize-time-resolution.md) (`cimd.Service`, the upsert's `created` flag, the `existing` row read during the freshness check) and [Part 5](2026-08-28-05-usage-limit.md) (`CIMDClientLimitExceeded`).

Models itself on [DCR Part 6](../dcr/2026-08-25-06-audit-log.md), which landed `oauth.client.registered` and the three `admin_api.mutation.*` events.

## 1. Goal / Scope

**Three** events. Nothing in the CIMD feature is auditable today: a third-party client can appear in a project, change its own redirect URIs, and be refused, all without leaving a trace an admin can see. The third closes the same gap on the DCR side.

| Event | When | Volume |
|---|---|---|
| `oauth.client.resolved` | a resolution **created** a record, or **changed** an existing one | once per client on creation, then only on actual metadata change |
| `oauth.client.resolution.failed` | a fetch, a validation, or the client limit refused a CIMD resolution | bounded by the [Part 4](2026-08-28-04-rate-limits.md) fetch limits (10/min/project by default) |
| `oauth.client.registration.failed` | `POST /oauth2/register` refused a DCR registration | bounded by DCR's own rate limits (10/min/IP, 1000/hour/project by default) |

**The third event is DCR, not CIMD.** It is here rather than in a plan of its own because it is one payload, one enum value and one emission site, and because it only became obvious while designing the CIMD pair — DCR has had the identical blind spot since it shipped. Part 6 already carries DCR-repairing work on the same basis. If it is preferred separate, commits 2 and 5 of §9 lift out cleanly.

Already covered, no work: **admin deletion** (`admin_api.mutation.delete_dynamic_client.executed`, source-agnostic, DCR Part 6 §2.4) and **rate-limit refusals** (`ratelimit.Limiter` dispatches a non-blocking event on every failed reservation — Part 4 §4).

Deliberately excluded: §7.

### 1.1 One success event, one failure event

An earlier draft of this part proposed four types, splitting creation from metadata change and the client limit from fetch failure. Collapsed to two, because in both cases the split was carrying a distinction the payload already expresses:

- **Creation and metadata change are the same act** — a successful resolution that wrote something. A `created` boolean and a `changes` list say which, and say it more precisely than two type names could (a record can be created, or changed in one field, or changed in five).
- **The client limit is one more way a resolution can fail to yield a usable client.** An `outcome` discriminator already exists on the failure event for the fetch/validation split; the limit is a third value of it.

Each merge costs one thing, both small enough to accept:

- **Type-level filtering of metadata changes is lost.** `pkg/admin/graphql/audit_log.go`'s activity-type filter is an enum over event types, so "show me every time a client changed its redirect URIs" now needs filtering on payload content rather than on type. Acceptable: an auditor investigating a client queries `oauth.client.resolved` for that `client_id` and reads the records, and there is no alerting path to lose — `ForHook()` is `false` (§2.3).
- **Cross-source reuse for the limit case is lost**, so DCR needs its own event rather than sharing one. A single `oauth.client.limit_exceeded` could have been emitted by both endpoints; `oauth.client.resolution.failed` cannot, because DCR registers rather than resolves. That is why §2.3 exists as a third event instead of a fourth `outcome` value — and it turns out to be the better outcome anyway, since DCR's failure modes barely overlap with CIMD's (§2.3).

### 1.2 `oauth.client.resolved`'s `changes` list is the first implementation of spec §8.4

Spec § Where resolution happens says the shared-record design "is what lets Authgear implement spec §8.4/§8.4.1's 'notice metadata changed compared to the last time it fetched' **in the future** (there is a real 'last fetch' to diff against)". The `changes` list is that future, and it is nearly free: `EnsureClientResolved` already holds both sides of the diff — `existing` from the freshness check (Part 3 §3.3 step 4) and `doc` from the fetch — so no extra query is needed.

It is also the highest-value part of this part. A CIMD client's metadata is controlled entirely by whoever can write to its URL; the single most dangerous change such a party can make is adding a `redirect_uri` they control, which turns every subsequent authorization into an authorization-code exfiltration. Nothing in Authgear notices that today. `changes` makes it visible after the fact, with old and new values side by side.

### 1.3 Why not reuse `oauth.client.registered`

Tempting for the success event: its payload already carries `Source`, the GraphQL enum value already exists, and an auditor filtering "third-party clients that appeared in my project" would get one type instead of two.

Rejected, because it contradicts the model the rest of the spec is built on. cimd.md is emphatic that a CIMD client is never registered — `registeredAt` is *always* `null`, and § Mapping to the Unified Client Model spells out "there is no registration event, only a fetch". An audit trail claiming `oauth.client.registered` for a client whose `registeredAt` is null is the kind of contradiction that costs someone an afternoon. Its `initial_access_token` field would also be permanently absent, which for DCR carries real meaning (DCR Part 6: an absent key means open registration) and here would mean nothing.

### 1.4 Naming, against the existing ~110 event types

`oauth.client.resolved` and `oauth.client.resolution.failed`. Both halves are settled by what the codebase already does (`grep -rhoP 'event\.Type = "\K[^"]+' pkg/api/event/{blocking,nonblocking}/*.go`):

- **The failure event is `<noun>.failed`**, matching `bot_protection.verification.failed` and `authentication.identity.login_id.failed`. An earlier draft used `oauth.client.resolution.failed` (the underscore compound of `fraud_protection.decision_recorded` and `user.deletion_scheduled`); the dotted form is the better precedent because those two are specifically *failure* events, which is the closer match.
- **The success event is a past participle, not `.success`.** Every one of the ~110 existing event types ends in a past participle — `sent`, `created`, `registered`, `connected`, `verified`, `updated`, `triggered`, `executed`, `authenticated`, `anonymized`, `promoted`, `blocked`, `failed`. The strings `success` and `succeeded` appear in **none** of them. So `oauth.client.resolution.success` would be the only event in the system named after a noun rather than something that happened.

The resulting pair is asymmetric, and that is also conventional: the codebase never pairs a success and a failure symmetrically. `email.sent` / `email.error` / `email.suppressed` are three sibling outcomes of one attempt rather than `email.send.{success,failed}`; the counterpart of `authentication.identity.login_id.failed` is `user.authenticated`, at a different path entirely; and `bot_protection.verification.failed` has no success counterpart at all.

The Admin API enum value is `OAUTH_CLIENT_RESOLUTION_FAILED` either way — dots and underscores both become underscores in the SCREAMING_CASE mapping (compare `BOT_PROTECTION_VERIFICATION_FAILED` at `audit_log.go:62`) — so this choice only affects the event-type string, not the filter surface.

## 2. Payloads — `pkg/api/event/nonblocking/`

### 2.1 `oauth_client_resolved.go`

```go
const OAuthClientResolved event.Type = "oauth.client.resolved"

type OAuthClientResolvedEventPayloadClient struct {
	ClientID        string                  `json:"client_id"`
	Source          model.OAuthClientSource `json:"source"`
	Kind            model.OAuthClientKind   `json:"kind"`
	ClientName      string                  `json:"client_name,omitempty"`
	ApplicationType string                  `json:"application_type,omitempty"`
	RedirectURIs    []string                `json:"redirect_uris"`
	GrantTypes      []string                `json:"grant_types"`
	ResponseTypes   []string                `json:"response_types"`
}

// OAuthClientResolvedEventPayloadChange is one changed field. Old and new
// are both included: they came from a document the client published
// publicly, so there is nothing to redact, and "redirect_uris went from X
// to Y" is the point of the record.
type OAuthClientResolvedEventPayloadChange struct {
	Field string `json:"field"`
	Old   any    `json:"old"`
	New   any    `json:"new"`
}

type OAuthClientResolvedEventPayload struct {
	Client OAuthClientResolvedEventPayloadClient `json:"client"`
	// Created is true on first resolution, false on a refetch that changed
	// something. It is the explicit discriminator: an auditor should not
	// have to infer it from Changes being absent.
	Created bool `json:"created"`
	// Changes is absent when Created, and otherwise non-empty -- the event
	// is not emitted for a refetch that changed nothing (§3.3).
	Changes []OAuthClientResolvedEventPayloadChange `json:"changes,omitempty"`
}
```

`Client` carries the post-resolution state in both cases, so a `created` record is complete on its own and a `changed` record shows the resulting client alongside the deltas.

The field set is deliberately the same as `OAuthClientRegisteredEventPayloadClient` minus the IAT. Do **not** factor the two into a shared struct: they are independent wire contracts documented separately in event.md, and coupling them means a future DCR-only field silently changes this event's shape.

`any` for `Old`/`New` because the fields are a mix of `string` and `[]string`. Separate string and slice change lists would be harder to read for no gain — this is a JSON document either way.

### 2.2 `oauth_client_resolution_failed.go`

```go
const OAuthClientResolutionFailed event.Type = "oauth.client.resolution.failed"

type OAuthClientResolutionOutcome string

const (
	// Unavailable covers EVERY transport-level failure as one
	// indistinguishable bucket: DNS, blocked address, connection refused,
	// TLS failure, timeout, non-2xx, oversize, unparseable body. See §4 --
	// do not subdivide this.
	OAuthClientResolutionOutcomeUnavailable OAuthClientResolutionOutcome = "unavailable"
	// Invalid means a JSON object was retrieved and failed a rule in
	// cimd.md's Accepted Metadata Fields.
	OAuthClientResolutionOutcomeInvalid OAuthClientResolutionOutcome = "invalid"
	// LimitExceeded means the document resolved cleanly but the project is
	// at its oauth_client_cimd quota, so no record was created.
	OAuthClientResolutionOutcomeLimitExceeded OAuthClientResolutionOutcome = "limit_exceeded"
)

type OAuthClientResolutionFailedEventPayload struct {
	ClientID string                       `json:"client_id"`
	Outcome  OAuthClientResolutionOutcome `json:"outcome"`
	// Reason names the validation rule that failed. Set only for the
	// "invalid" outcome; absent otherwise. See §4.
	Reason string `json:"reason,omitempty"`
	// UsageName and Quota are set only for "limit_exceeded".
	UsageName model.UsageName `json:"usage_name,omitempty"`
	Quota     int             `json:"quota,omitempty"`
	// ServedStaleRecord is true when a persisted record already existed and
	// was served despite this failure (Part 3 §5), false when the client was
	// left unresolvable. Always false for "limit_exceeded", which only
	// arises when there was no record to begin with. This is Authgear's own
	// state, not a property of the target, so it is safe to report -- and it
	// is the difference between "your client is degraded" and "your client
	// is broken".
	ServedStaleRecord bool `json:"served_stale_record"`
}
```

The outcome-specific `omitempty` fields make this a mild grab-bag, which is the normal shape for an event with a discriminator. The alternative — one type per outcome — is what §1.1 rejected.

**`limit_exceeded` is safe as a distinguishable outcome**, and the spec says so directly: § Error Handling calls the client-limit case "not a fetch-outcome signal — it doesn't vary by target host or reveal anything about network reachability — so it falls outside the uniform-error rule". It does imply the fetch succeeded, since the limit is only checked after a document validates (Part 5 §3) — but reaching that point requires the target to serve a valid CIMD document whose `client_id` equals the probe URL, which no arbitrary host will do. Same reasoning as why a *successful* resolution is not an oracle.

### 2.3 `oauth_client_registration_failed.go` — the DCR counterpart

```go
const OAuthClientRegistrationFailed event.Type = "oauth.client.registration.failed"

type OAuthClientRegistrationOutcome string

const (
	// The Authorization header was malformed, an initial access token was
	// required and absent, or the token presented was unknown or expired.
	// Reason distinguishes which: "malformed_header", "not_presented",
	// "unknown", "expired".
	OAuthClientRegistrationOutcomeInvalidInitialAccessToken OAuthClientRegistrationOutcome = "invalid_initial_access_token"
	// The body was not a JSON object, or failed a rule in dcr.md's Accepted
	// Client Metadata.
	OAuthClientRegistrationOutcomeInvalidClientMetadata OAuthClientRegistrationOutcome = "invalid_client_metadata"
	// The project is at its oauth_client_dcr quota.
	OAuthClientRegistrationOutcomeLimitExceeded OAuthClientRegistrationOutcome = "limit_exceeded"
)

type OAuthClientRegistrationFailedEventPayload struct {
	Outcome OAuthClientRegistrationOutcome `json:"outcome"`
	// Reason names the specific cause within the outcome. Always set for
	// "invalid_initial_access_token" and "invalid_client_metadata"; absent
	// for "limit_exceeded", which has no sub-cases.
	Reason string `json:"reason,omitempty"`
	// UsageName and Quota are set only for "limit_exceeded".
	UsageName model.UsageName `json:"usage_name,omitempty"`
	Quota     int             `json:"quota,omitempty"`
	// InitialAccessToken identifies the token that was rejected. Present
	// only when reason is "expired" -- an unknown token has no row to
	// describe, and none was presented in the "not_presented" case. Never
	// the token value, and never a hash of it (a hash is still a guessing
	// oracle); the ID is the row uuid the Admin API already exposes.
	// Shared with oauth.client.registered -- see §2.3.1.
	InitialAccessToken *EventPayloadInitialAccessToken `json:"initial_access_token,omitempty"`
}
```

**Why the outcomes are DCR's own rather than CIMD's three.** The two endpoints fail for almost entirely different reasons. `POST /oauth2/register` has no fetch, so `unavailable` is meaningless; CIMD has no initial access token, so IAT rejection is meaningless. Only `limit_exceeded` is common, which is not enough shared surface to justify one type — and forcing one would have meant an event whose valid `outcome` values depend on which endpoint emitted it.

**There is no oracle constraint here, and the `reason` field is deliberately unrestricted.** This is the important thing not to copy from §4. CIMD's uniform failure surface exists because the fetch target is attacker-chosen, so any distinguishable outcome leaks network reachability. `POST /oauth2/register` fetches nothing — there is no third party in the picture and nothing to probe. It also already returns a *detailed* RFC 7591 error to the caller (`handler_register.go` maps every `dcr.ErrDCR*` sentinel to its own `(error, status)` pair), so withholding the reason from the project's own audit log would protect nothing while making the record useless. `reason` therefore carries the specific rule: `malformed_json`, `redirect_uris_missing`, `redirect_uri_invalid`, `grant_type_unsupported`, `response_type_inconsistent`, `application_type_unsupported`, `token_endpoint_auth_method_not_accepted`, `uri_field_not_https`.

**Including within `invalid_initial_access_token`.** An earlier draft collapsed "unknown token" and "expired token" into one indistinguishable value, reasoning that separating them is a guessing oracle. That was wrong, and wrong in the same way as importing §4's rule here would be: the guessing oracle governs the **HTTP response**, which the guesser sees, not the **audit log**, which only the project admin can read. An unauthenticated caller working through invented tokens learns nothing from a record they cannot fetch.

And the distinction is worth a lot to the admin, because the two are different incidents:

- **`expired`** — an integration broke. Rotate or reissue the token. Operational.
- **`unknown`** — either someone is guessing, or a revoked token is still in use by a stale deployment. Security.

Conflating them makes the record nearly useless for the case it exists to serve. `reason` therefore takes `malformed_header`, `not_presented`, `unknown` or `expired`, and `initial_access_token` is populated for `expired` — the only one of the four where a token row exists to describe.

**What does not change: the HTTP response.** `POST /oauth2/register` still returns the same `invalid_initial_access_token` error with the same status for all four reasons, so the caller learns nothing. This is exactly the split CIMD uses — uniform response, detailed audit record — applied to a different threat.

**The payload carries no `client_id`, and neither does its context** — no client was created, so none exists. `FillContext` therefore sets nothing, and `UserID()` is `""` like the other two. The record is still identifiable: `event.Context` supplies `IPAddress`, `UserAgent`, `Timestamp`, `AppID` and `AuditContext["http_url"]` (`pkg/api/event/context.go:32-47`), and IP plus timestamp is exactly what an admin needs to recognise someone working through a list of guessed initial access tokens.

#### 2.3.1 The initial-access-token sub-object is shared with `oauth.client.registered`

`oauth.client.registered` already carries an IAT sub-object, `OAuthClientRegisteredEventPayloadInitialAccessToken`, but with only `{id, type}` — so without this, an auditor correlating "which clients did leaked token X register, and when did it stop working" would read two different shapes for the same token.

**One shared type, used by both events.** This is the opposite call from §2.1's "do not factor the two client structs together", and deliberately so: there the two shapes should be free to diverge, because a future DCR-only client field must not silently change CIMD's payload. Here the requirement is that they *never* diverge — the point is that a token presents identically in both records — so sharing makes it a compile-time guarantee rather than a convention that drifts.

New file `pkg/api/event/nonblocking/oauth_initial_access_token.go`. A standalone shared type in this package has precedent in `project.go`'s `AppConfig`:

```go
package nonblocking

// EventPayloadInitialAccessToken describes an initial access token in an
// audit event payload. Shared by oauth.client.registered and
// oauth.client.registration.failed so a token presents identically in both.
//
// Never carries the token value or a hash of it (a hash is still a guessing
// oracle). ID is the row uuid the Admin API already exposes.
type EventPayloadInitialAccessToken struct {
	ID        string                            `json:"id"`
	Type      model.OAuthInitialAccessTokenType `json:"type"`
	CreatedAt time.Time                         `json:"created_at"`
	ExpiresAt time.Time                         `json:"expires_at"`
}

// NewEventPayloadInitialAccessToken maps nil to nil, which is what both
// callers want: open registration presents no token, and an unknown or
// absent one has no row to describe. Combined with `omitempty` on the field,
// that drops the key entirely rather than emitting an object of zero values.
func NewEventPayloadInitialAccessToken(iat *model.OAuthInitialAccessToken) *EventPayloadInitialAccessToken {
	if iat == nil {
		return nil
	}
	return &EventPayloadInitialAccessToken{
		ID:        iat.ID,
		Type:      iat.Type,
		CreatedAt: iat.CreatedAt,
		ExpiresAt: iat.ExpiresAt,
	}
}
```

`dcr.InitialAccessToken.ToModel()` already populates `Meta.CreatedAt` and `ExpiresAt` (`pkg/lib/dcr/initial_access_token.go:26-38`), so nothing new has to be stored or plumbed.

Changes to the shipped event:

- `OAuthClientRegisteredEventPayload.InitialAccessToken` changes type to `*EventPayloadInitialAccessToken`; delete `OAuthClientRegisteredEventPayloadInitialAccessToken`.
- `handler_register.go:269`'s literal becomes `nonblocking.NewEventPayloadInitialAccessToken(iat)`, which also removes the `if iat != nil` guard around it.
- `docs/specs/event.md`'s `oauth.client.registered` section gains the two keys.

**This is backward-compatible.** `id` and `type` keep their JSON names, so the change is purely additive to the emitted object, and the event is `ForHook() == false` — audit-only, read through the Admin API's audit-log `data` blob, with no webhook consumer to break. The existing comment on that field (DCR Part 6: an absent key means open registration) stays true and stays valuable.

**Outcomes deliberately not recorded**, on the same principle as §7's CIMD exclusions — an admin must learn something they do not already have:

- **DCR disabled.** A static config answer the admin owns.
- **Rate limited.** `ratelimit.Limiter` already dispatches its own event on every failed reservation.

### 2.4 Shared payload contract

All three follow `oauth_client_registered.go` exactly: `UserID() == ""`, `GetTriggeredBy() == event.TriggeredByTypeUser`, `ForHook() == false`, `ForAudit() == true`, and a `FillContext` that sets `ctx.ClientID`.

`UserID() == ""` matters — CIMD resolution happens at `/oauth2/authorize` *before* the user authenticates, so there is genuinely no user, exactly as for `oauth.client.registered` and `m2m.token.created`. `ctx.ClientID` is therefore the only identifier the two CIMD records carry (§2.3's has none at all), which is why §8 asks for it to be documented as part of each event's contract.

`ForHook() == false` on all three: these are audit records, not webhook triggers. A blocking hook on the authorize path would put a customer's HTTP endpoint in the critical path of every new client resolution, and a non-blocking one adds queue volume for no stated use case. If a project wants them delivered, that is a separate decision.

## 3. Emission

### 3.1 `pkg/lib/cimd` — two dispatch styles, because the failure event has no transaction

This is the one non-obvious piece of wiring.

`oauth.client.resolved` is emitted from inside `Service.upsert`, which runs inside `Database.WithTx` (Part 3 §3.3 step 8), so it uses **`DispatchEventOnCommit`** — the same call `handler_register.go:205` uses. That is also correct semantically: it must not be recorded if the upsert rolls back.

`oauth.client.resolution.failed` cannot use it, for either of its two paths. On a fetch failure no transaction was ever opened; on the `limit_exceeded` path the transaction is about to roll back, so `OnCommit` would drop exactly the record you need. It uses **`DispatchEventImmediately`**, wrapped in the `IsInTx`/`ReadOnly` branch that `usage.Limiter.dispatchEventImmediately` (`pkg/lib/usage/limit.go:393-403`) already establishes:

```go
type ServiceEventService interface {
	DispatchEventOnCommit(ctx context.Context, payload event.Payload) error
	DispatchEventImmediately(ctx context.Context, payload event.NonBlockingPayload) error
}

func (s *Service) dispatchImmediately(ctx context.Context, payload event.NonBlockingPayload) {
	dispatch := func(ctx context.Context) error {
		return s.Events.DispatchEventImmediately(ctx, payload)
	}
	var err error
	if s.Database.IsInTx(ctx) {
		err = dispatch(ctx)
	} else {
		err = s.Database.ReadOnly(ctx, dispatch)
	}
	if err != nil {
		// An audit-log failure must never fail the authorization request.
		ServiceLogger.GetLogger(ctx).WithError(err).
			Error(ctx, "cimd: failed to dispatch audit event")
	}
}
```

The swallowed error is deliberate: an audit write failing must not convert a resolvable client into an error, nor a clean failure into a `server_error`. It is logged instead. Note the asymmetry with `DispatchEventOnCommit`, whose error *is* returned — there the transaction has not committed yet, so failing is safe, and the alternative is a committed row with no audit record.

For the `limit_exceeded` path, dispatch **before** returning `ErrClientLimitExceeded` from `upsert`, while still inside the transaction that is about to roll back. `DispatchEventImmediately` writes through its own path rather than the caller's transaction, so the rollback does not take the record with it — **verify this against `event.Service.DispatchEventImmediately` (`pkg/lib/event/service.go:107`) during implementation**, and if it does participate in the caller's transaction, move the dispatch to after `WithTx` returns in `EnsureClientResolved`.

### 3.2 Computing the diff

In `Service.upsert`, when `created == false`, compare `existing` (already in hand) against `doc`:

```go
func diffClientMetadata(existing *oauthclient.Client, doc *Document) []nonblocking.OAuthClientResolvedEventPayloadChange {
	var changes []nonblocking.OAuthClientResolvedEventPayloadChange
	addString := func(field string, old *string, new *string) { /* normalize nil/"" then compare */ }
	addSet := func(field string, old []string, new []string) { /* setutil comparison */ }

	addString("client_name", existing.ClientName, doc.ClientName)
	addString("client_uri", existing.ClientURI, doc.ClientURI)
	addString("logo_uri", existing.LogoURI, doc.LogoURI)
	addString("tos_uri", existing.TOSURI, doc.TOSURI)
	addString("policy_uri", existing.PolicyURI, doc.PolicyURI)
	if existing.ApplicationType != doc.ApplicationType { /* ... */ }
	addSet("redirect_uris", existing.RedirectURIs, doc.RedirectURIs)
	addSet("grant_types", existing.GrantTypes, doc.GrantTypes)
	addSet("response_types", existing.ResponseTypes, doc.ResponseTypes)

	return changes
}
```

Four details decide whether `changes` is signal or noise:

- **Only document-derived fields.** Never `last_fetched_at` or `updated_at` — they change on every refetch by construction, so including them would make the event fire hourly for every client and render it useless.
- **Normalize `client_name` the same way storage does.** `Store.NewClient` maps an explicit `""` to `nil` (`store_client.go:535-538`), so a document that switches between omitting `client_name` and sending `""` must not register as a change. Compare after the same normalization, using the shared helper Part 3 §2.1 asks for.
- **Slice fields compare as sets, not sequences.** Order carries no meaning in `redirect_uris`, `grant_types` or `response_types`, so a document that merely reorders entries is not a change worth a record. Use `setutil` (`pkg/util/setutil`). Report the new value as stored, not as a sorted set.
- **`existing` may be up to 5 minutes stale**, since the freshness read is cache-first (Part 3 §4.2). The only writer to that row is this same path under a single-flight guard, so a false "changed" is very unlikely — and if it happens the record is a duplicate rather than wrong, which is the acceptable direction. Do not add a re-read to close this; it would put a Postgres round-trip on the hot path to improve an audit record.

### 3.3 `pkg/lib/cimd` — emission points

Against Part 3 §3.3's numbered steps:

| Step | Condition | Event | Dispatch |
|---|---|---|---|
| (7) fetch/validate failed, `existing == nil` | always | `resolution.failed`, `unavailable`/`invalid`, `served_stale_record: false` | Immediately |
| (7) fetch/validate failed, `existing != nil` | always | `resolution.failed`, `unavailable`/`invalid`, `served_stale_record: true` | Immediately |
| (8) `upsert`, limit refused | `created && limitErr != nil` | `resolution.failed`, `limit_exceeded`, with `usage_name` and `quota` | Immediately, before returning |
| (8) `upsert`, created | `created` | `resolved`, `created: true`, no `changes` | OnCommit |
| (8) `upsert`, updated | `!created && len(changes) > 0` | `resolved`, `created: false`, with `changes` | OnCommit |
| (8) `upsert`, updated | `!created && len(changes) == 0` | **none** | — |

The last row is the point of the design: a successful refetch that changed nothing is the routine hourly case and carries no information.

`allowed_domains` refusals and `insecure_http_allowed`-driven rejections also emit nothing — they never reach the fetch, and they are a static policy answer the admin can read off their own config. Only outcomes that involved an actual attempt are recorded.

### 3.4 `POST /oauth2/register` — the DCR emission

`RegistrationHandler` already has an `Events EventService` field and already emits `oauth.client.registered` on success (`handler_register.go:205`), so this adds emission sites, not plumbing. Its `EventService` interface (`handler_token.go:78-81`) declares only `DispatchEventOnCommit`, so **add `DispatchEventImmediately` to it** — every failure path needs it, for the same two reasons as §3.1: the early failures precede any transaction, and the IAT and quota failures sit inside a `WithTx` that is about to roll back.

Against `Handle`'s existing sequence:

| Point in `Handle` | Outcome | Payload detail |
|---|---|---|
| DCR not enabled | — | no event (§2.3) |
| per-IP / per-project rate limit | — | no event, `ratelimit.Limiter` covers it |
| `Authorization` header present but not `Bearer ` | `invalid_initial_access_token` | `reason: "malformed_header"` |
| no token and `IsInitialAccessTokenRequired()` | `invalid_initial_access_token` | `reason: "not_presented"` |
| `json.NewDecoder(...).Decode` fails | `invalid_client_metadata` | `reason: "malformed_json"` |
| `dcr.ValidateAndNormalize` fails | `invalid_client_metadata` | `reason` = the sentinel's rule name |
| inside `WithTx`: `ValidateAndGetByToken` → `ErrInitialAccessTokenNotFound` | `invalid_initial_access_token` | `reason: "unknown"` |
| inside `WithTx`: `ValidateAndGetByToken` → `ErrInitialAccessTokenExpired` | `invalid_initial_access_token` | `reason: "expired"`, with `initial_access_token` |
| inside `WithTx`: `UsageLimiter.CheckStanding` fails | `limit_exceeded` | `usage_name: oauth_client_dcr`, `quota` |
| `DCR.RegisterClient` or any other infrastructure error | — | no event; a 500 is not an audit outcome |

**`dcr.Queries.ValidateAndGetByToken` has to start distinguishing expiry.** Today it cannot: it looks the token up by hash and, on expiry, discards the row and returns `ErrInitialAccessTokenNotFound` — the same error as for an unknown token (`pkg/lib/dcr/queries.go`). So the handler has no way to populate `initial_access_token`, or even to tell `unknown` from `expired`.

Add a sentinel and return the model alongside it:

```go
// pkg/lib/dcr/errors.go
var ErrInitialAccessTokenExpired = apierrors.NotFound.WithReason("InitialAccessTokenExpired").New("initial access token expired")

// pkg/lib/dcr/queries.go — ValidateAndGetByToken
//
// Returns a NON-NIL token together with ErrInitialAccessTokenExpired: the
// caller must reject the registration, but the audit event needs the row to
// describe. Check the error first; the token is for reporting only, never
// for authorizing. This is deliberate, not a slip -- do not "fix" it to
// return nil.
if !t.ExpiresAt.After(q.Clock.NowUTC()) {
    return t.ToModel(), ErrInitialAccessTokenExpired
}
```

The handler maps **both** sentinels to the identical HTTP error, so response behavior is unchanged; only the audit `reason` and the presence of `initial_access_token` differ. The existing comment on that function — "both cases must be indistinguishable to the caller" — needs amending to say *in the response*, and to point at this part for why the audit log distinguishes them.

Reuse §3.1's `dispatchImmediately` shape rather than writing a second one — same `IsInTx`/`ReadOnly` branch, same swallow-and-log on failure, same reasoning (an audit write must never turn a 400 into a 500). Factor it into a small helper both `cimd.Service` and `RegistrationHandler` can call, or duplicate the six lines; do not let one of them return the dispatch error while the other swallows it.

`reason` values must come from a mapping keyed on the sentinel, alongside the existing `mapDCRValidationError` that already maps each one to its RFC 7591 `(error, status)` pair. Extending that function to return the audit reason too keeps the two in one place, so a new validation rule cannot get an HTTP error without also getting an audit reason.

**The quota row is the one that motivated this event.** Today a project at its `oauth_client_dcr` quota sees registrations fail with `access_denied` and nothing else: `usage.Limiter.ReportStandingCreated` fires only on a *successful* create that crosses a threshold, never on a block, so an exhausted quota is invisible until a developer complains. Same asymmetry Part 5 §5 describes for CIMD.

## 4. The `reason` field, and the oracle constraint

The audit log is readable by the **project admin**, who in a multi-tenant deployment is a customer, not the operator. That makes it a second, *authenticated* channel for the probing attack spec § Authgear as an SSRF/Probing Oracle addresses on the unauthenticated one — and one at higher privilege, since the uniform `unauthorized_client` response deliberately tells an anonymous caller nothing.

If `resolution.failed` carried a transport-level reason — "connection refused" vs "TLS handshake failed" vs "timeout" — a tenant admin could enumerate the operator's internal network by sending authorization requests with crafted `client_id`s and reading their own audit log. The address filter (Part 2 §2.3) is what actually prevents reaching those hosts, but defence in depth is the whole reason the error surface is uniform in the first place.

**The rule: `outcome: "unavailable"` is one bucket covering every transport failure, and carries no `reason`.** DNS failure, blocked address, connection refused, TLS error, timeout, non-2xx, oversize body and unparseable JSON are all indistinguishable in the audit log, exactly as they are in the HTTP response.

**`outcome: "invalid"` does carry a `reason`**, naming the validation rule that failed — `client_id_mismatch`, `redirect_uris_missing`, `redirect_uri_invalid`, `token_endpoint_auth_method_not_accepted`, and so on, one per `ErrDocument*` sentinel ([Part 2](2026-08-28-02-document-fetching.md) §3). This is safe and it is the point of the field: reaching `invalid` at all means the host returned a parseable JSON object, so the reason describes **the client author's own published document**, which they can read themselves. It reveals nothing about network topology, and it is the only thing that makes a misconfigured CIMD document debuggable — today a developer with a typo gets `unauthorized_client` and no way to find out why.

**`outcome: "limit_exceeded"` carries `usage_name` and `quota`** and no `reason`. Safe per §2.2.

Two things to hold in review:

- **Never subdivide `unavailable`.** Not for "debuggability", not behind a config flag, not "only in dev mode". The moment it distinguishes network states it becomes the oracle.
- **`invalid` must be reached only after a successful parse.** The classification comes from which function returned the error — `Fetcher.Fetch` is always `unavailable`, `ParseAndValidate` is always `invalid`, the limit check is always `limit_exceeded` — never from inspecting the error's content. If a future refactor lets a transport error fall into the `invalid` branch, the guarantee is gone.

## 6. Fixed Behavioral Decisions

- **D1. Two event types, not four.** §1.1. Creation and metadata change are the same act, distinguished by `created` and `changes`; the client limit is a third `outcome` value on the failure event.
- **D2. `oauth.client.resolved` is not emitted for a refetch that changed nothing.** The routine hourly case carries no information; emitting it would bury the records that matter. This survives the merge — it is the rule that keeps the merged event's volume identical to the two-event design.
- **D3. `Created` is an explicit field, not inferred from `Changes` being absent.** An auditor should not have to derive the discriminator.
- **D4. Only document-derived fields are diffed**, never `last_fetched_at`/`updated_at`, which change on every refetch by construction.
- **D5. Slice fields diff as sets; `client_name` diffs after storage normalization.** A reorder or an `""`↔absent switch is not a change.
- **D6. `unavailable` carries no reason, ever.** §4. The audit log is an authenticated channel at higher privilege than the uniform HTTP error, and a tenant admin must not be able to use it to probe the operator's network.
- **D7. `invalid` does carry the failing rule**, because reaching it proves a parseable document was retrieved, so the reason describes the client author's own published content.
- **D8. `limit_exceeded` is distinguishable, per spec § Error Handling's explicit carve-out** from the uniform-error rule.
- **D9. The outcome is classified by which function failed**, not by inspecting the error.
- **D10. `resolved` dispatches OnCommit; `resolution.failed` dispatches Immediately.** §3.1. The failure event either has no transaction or has one about to roll back.
- **D11. An audit dispatch failure on the Immediately path is logged and swallowed.** It must never turn a resolvable client into an error, or a clean failure into a `server_error`.
- **D12. `ForHook() == false` on both.** Audit records, not webhook triggers.
- **D13. DCR gets its own event, `oauth.client.registration.failed`, rather than sharing CIMD's.** §2.3: the two endpoints' failure modes barely overlap — no fetch on one side, no initial access token on the other — so one type would have had `outcome` values whose validity depended on the emitter.
- **D14. `existing` being up to 5 minutes stale is accepted.** A false `changes` entry is a duplicate record, not a wrong one, and closing it would add a Postgres read to the hot path for an audit record's benefit.
- **D15. `oauth.client.registration.failed` has no oracle constraint, and its `reason` is unrestricted.** §2.3. `POST /oauth2/register` fetches nothing, so there is no reachability to leak, and it already returns a detailed RFC 7591 error to the caller. Do not copy §4's uniform-failure rule onto it.
- **D16. `invalid_initial_access_token` distinguishes four reasons — `malformed_header`, `not_presented`, `unknown`, `expired` — and carries the token's row for `expired`.** An earlier draft collapsed unknown and expired, on a guessing-oracle argument that applies to the HTTP *response* (which the guesser sees) and not to the audit log (which only the admin can read). The two are different incidents: `expired` is a broken integration to reissue, `unknown` is guessing or a revoked token still in use. The HTTP response stays identical across all four.
- **D17. Never log the token value or a hash of it.** The `id` is the row uuid the Admin API already exposes and is safe; a hash of the token is not, since it is still a guessing oracle.
- **D17a. One shared `EventPayloadInitialAccessToken`, used by both `oauth.client.registered` and `oauth.client.registration.failed`.** §2.3.1. Opposite call from §2.1's separate client structs, and deliberately: those should be free to diverge, this must never. Adds `created_at`/`expires_at` to the shipped success event — purely additive, and it is `ForHook() == false` so there is no webhook consumer to break.
- **D18. `oauth.client.registration.failed` carries no `client_id` in payload or context**, because no client was created. `event.Context`'s `IPAddress`/`UserAgent`/`Timestamp`/`http_url` identify the record, which is what makes IAT guessing recognisable.
- **D19. `ValidateAndGetByToken` returns a non-nil token together with `ErrInitialAccessTokenExpired`.** §3.4. Unusual in Go and therefore explicitly intended: the caller must reject the registration, and the audit event needs the row. Check the error first; the token is for reporting only.

## 7. Considered and Rejected

- **An event per successful resolution, changed or not.** One per client per hour carrying no information in the overwhelming majority of cases — the classic way an audit log becomes unreadable. This is what D2 prevents, and it is the trap the merge in §1.1 could have introduced if `resolved` had been defined as "every successful resolution".
- **Logging that an insecure fetch flag was used** (Part 1 D16). Already a server-side `Warn` with `app_id` and target host, which is the right audience: the flags are set by the operator through Site Admin, and a tenant-visible record saying "your project's SSRF protections are disabled" would alarm an admin about something they can neither see nor change.
- **Logo fetch outcomes** ([Part 7](2026-08-28-07-logo-proxy.md)). High volume, cosmetic consequence, no security value. Server log only.
- **`allowed_domains` / disabled-CIMD refusals.** No attempt was made; the answer is a static function of config the admin already has. Recording them would generate volume proportional to attack traffic while telling the admin only what they configured.
- **A separate "stale record served" event.** Covered by `served_stale_record` — a distinct event would double the volume for the same information.
- **Including the fetched document body.** Up to 5 KB per record, mostly unchanged between fetches, and every field that matters is already in `client` and `changes`.
