# CIMD Part 4 — Denial-of-Service Rate Limits on Attacker-Chosen Fetch Targets

Spec: [docs/specs/cimd.md — Denial of Service via Attacker-Chosen Fetch Targets](../../specs/cimd.md#denial-of-service-via-attacker-chosen-fetch-targets).

Depends on [Part 3](2026-08-28-03-authorize-time-resolution.md) (`cimd.Service`, and specifically the `ServiceRateLimiter` seam it left bound to a no-op).

## 1. Goal / Scope

Replace Part 3's no-op `ServiceRateLimiter` with two token buckets, configurable per plan tier in `authgear.features.yaml`, and delete the no-op.

The threat, restated from the spec so the numbers below have something to be justified against: a `client_id` can point at **any** internet host, and both the resolver cache and the `(app_id, client_id)` unique index are keyed on the exact URL string — not the hostname. So an attacker can force a fresh fetch on every request while still hammering one victim host, simply by appending a different query string each time. Authgear becomes a free, unauthenticated HTTP amplifier pointed wherever the attacker likes.

| Limit | Default | Prevents |
| --- | --- | --- |
| Per project (`app_id`) | 10 / minute | One project exceeding a reasonable total, regardless of target |
| Per (project, caller IP) | 5 / minute | One caller consuming the project's whole allowance |

Two deviations from spec § Denial of Service, both deliberate; §5 updates the spec.

### 1.1 The per-(project, host) bucket is dropped

Spec § Denial of Service specifies a third bucket: 5/minute per (project, host), to stop "one project's traffic concentrating entirely on a single external host". It is not built, because as specified it buys almost nothing:

- **The per-project bucket already caps harm to any single victim** at the project's total rate. The per-host bucket only binds when a project's fetches are *all* aimed at one host, and then it changes the sustained load on that victim from 10/min to 5/min. A factor of two, for an extra Redis round-trip on every fetch and an attacker-influenced string in the key space.
- **It was never aggregate protection.** The spec scopes it per project explicitly — "so it never throttles an unrelated project sharing that host" — so it does nothing against the case that actually matters for a victim, which is many projects (or many tenants of a shared deployment) pointed at the same host. The control that would matter there is a **global**, cross-project per-host bucket, and that is a different design with real cross-tenant availability tradeoffs. It is not this one, and building this one does not get you closer to it.
- With the per-IP bucket now defaulting to 5/minute (§1.2), the per-host bucket carries the same number as a bucket that already applies to every fetch.

If victim-oriented limiting is wanted later, add it as the global bucket, and make that decision on its own merits.

### 1.2 Per-IP drops from 20 to 5 per minute

Spec § Denial of Service says 20/minute per caller IP. That is far too loose, because of a property of the design the spec's number predates: **the buckets count fetches, not requests, and fetches are deduplicated per `client_id`.**

A given `client_id` is fetched at most once per `RefetchInterval` (1 hour), and concurrent attempts collapse through the single-flight guard (Part 3 §4.3). So the legitimate per-IP fetch volume is not driven by user traffic at all:

- An MCP client installed on a thousand machines behind one corporate NAT publishes **one** `client_id`, so all of them together cause one fetch per hour. NAT aggregation does not multiply fetches.
- A first-time authorization for a new client costs exactly **one** fetch.
- To exceed 5 fetches/minute from a single IP, a caller has to present 6+ *distinct, new-or-stale* `client_id`s within a minute — which is what minting novel URLs looks like, and is not what any real client does.

5/minute leaves headroom for a user retrying a failing onboarding a few times, and for a handful of distinct clients being set up together. It also makes the per-IP bucket **tighter than the per-project bucket**, which is the sensible relationship and was not true before: at 20 vs 10 the per-IP bucket could never bind first, so it did no work.

The case it does squeeze is a developer iterating on their own document by varying its URL. That is exactly what §2's configurability is for — a test project raises its own limits.

### 1.3 The limits are configurable, in feature config only

An earlier draft of this plan argued they should be fixed, on the grounds that "a project owner raising the ceiling is spending someone else's budget." That reasoning is sound and it is **why the config lives in `authgear.features.yaml` rather than `authgear.yaml`**: feature config is written only through the Site Admin surface (`pkg/siteadmin/service/feature_config.go`), never the tenant portal, so the person who can raise the ceiling is the operator who runs Authgear and owns its egress reputation — precisely the right person. It is not project-configurable in the sense that matters.

What the earlier draft got wrong was concluding "therefore fixed". Fixed means the operator has **no lever short of a code change**, and there are two situations where that is the wrong answer:

- A large customer with genuinely high CIMD onboarding volume on an enterprise plan needs more than 10 fetches/minute, and there is nothing pathological about that.
- §4's residual risk — an attacker keeping the shared per-project bucket empty and blocking legitimate onboarding — currently has no mitigation at all. With a plan-tier knob the operator can raise the ceiling during an incident.

Note the asymmetry with DCR, which puts its registration rate limits in `authgear.yaml` (tenant-editable). That is justified rather than inconsistent: DCR registration load lands on **Authgear's own database**, so the tenant bearing it is the right person to tune it; a CIMD fetch lands on a **third party's** server, so the operator is.

```go
type OAuthClientIDMetadataDocumentRateLimitsFeatureConfig struct {
	PerProject *RateLimitConfig `json:"per_project,omitempty"`
	PerIP      *RateLimitConfig `json:"per_ip,omitempty"`
}

// SetDefaults mirrors OAuthDynamicClientRegistrationRateLimitsConfig's:
// PerProject/PerIP are non-nil by the time this runs (SetFieldDefaults
// force-allocates them), so Enabled == nil detects "never configured".
func (c *OAuthClientIDMetadataDocumentRateLimitsFeatureConfig) SetDefaults() {
	if c.PerProject.Enabled == nil {
		c.PerProject = &RateLimitConfig{Enabled: new(true), Period: "1m", Burst: 10}
	}
	if c.PerIP.Enabled == nil {
		c.PerIP = &RateLimitConfig{Enabled: new(true), Period: "1m", Burst: 5}
	}
}

func (c *OAuthClientIDMetadataDocumentRateLimitsFeatureConfig) Merge(layer *OAuthClientIDMetadataDocumentRateLimitsFeatureConfig) *OAuthClientIDMetadataDocumentRateLimitsFeatureConfig {
	if c == nil && layer == nil {
		return nil
	}
	if c == nil {
		return layer
	}
	if layer == nil {
		return c
	}
	// Whole-bucket replacement: enabled/period/burst are one unit, and
	// merging them field-wise would let a layer produce a bucket neither
	// layer wrote.
	if layer.PerProject != nil {
		c.PerProject = layer.PerProject
	}
	if layer.PerIP != nil {
		c.PerIP = layer.PerIP
	}
	return c
}
```

`OAuthClientIDMetadataDocumentFeatureConfig.Merge` (Part 1 §2.4) gains `merged.RateLimits = merged.RateLimits.Merge(layer.RateLimits)`, and a nil-safe `GetRateLimits()` accessor.

Two facts that make this cheap, both verified:

- **`RateLimitConfig` is already registered in `FeatureConfigSchema`** (`pkg/lib/config/rate_limit.go:19`, alongside its `Schema` registration at line 5), so `$ref: "#/$defs/RateLimitConfig"` resolves with no new registration.
- **Defaults are applied after the merge, not per layer.** `AuthgearFeatureYAMLDescriptor.viewEffectiveResource` parses each layer with `ParseFeatureConfigWithoutDefaults`, merges, then re-parses the marshalled result with `ParseFeatureConfig` (which runs `SetFieldDefaults`). So a layer that omits `rate_limits` really does have `nil`, and `SetDefaults` fills the built-in rates exactly once at the end.

Check during implementation whether the new struct needs a `nullable:"true"` tag for `SetFieldDefaults` to behave (compare `FeatureConfig.Usage`, `feature.go:52`), and make the §7 merge test cover "a later layer omits `rate_limits`" either way.

Setting `enabled: false` on a bucket disables it entirely — `ratelimit.Limiter.doReserveN` short-circuits on `!spec.Enabled`. That is the intended way for an operator to turn a bucket off for a test project, and it is why §7 tests it.

## 3. `pkg/lib/cimd/ratelimit.go` — bucket specs and the limiter

### 3.1 Bucket specs

The specs live in `pkg/lib/cimd`, not `pkg/lib/oauth/handler/ratelimit.go`. The DCR register buckets live in the handler package because the handler consumes them; here the consumer is `cimd.Service`, and keeping the specs beside it avoids `pkg/lib/cimd` importing `pkg/lib/oauth/handler`.

```go
package cimd

func NewBucketSpecCIMDFetchPerProject(rateLimits *config.OAuthClientIDMetadataDocumentRateLimitsFeatureConfig) ratelimit.BucketSpec {
	// No args: BucketSpec.IsGlobal is false, so Limiter keys by app id via
	// bucketKeyApp (pkg/lib/ratelimit/limiter.go:171-173).
	return ratelimit.NewBucketSpec(
		ratelimit.RateLimitOAuthCIMDFetchPerProject,
		ratelimit.RateLimitGroupOAuthCIMDFetch,
		rateLimits.PerProject,
		ratelimit.OAuthCIMDFetchPerProject,
	)
}

func NewBucketSpecCIMDFetchPerIP(rateLimits *config.OAuthClientIDMetadataDocumentRateLimitsFeatureConfig, ip string) ratelimit.BucketSpec {
	return ratelimit.NewBucketSpec(
		ratelimit.RateLimitOAuthCIMDFetchPerIP,
		ratelimit.RateLimitGroupOAuthCIMDFetch,
		rateLimits.PerIP,
		ratelimit.OAuthCIMDFetchPerIP,
		ip,
	)
}
```

These take the resolved config rather than constructing a `config.RateLimitConfig` literal, so the built-in rates live in `SetDefaults()` and are not duplicated here — the same shape as `NewBucketSpecOAuthRegisterPerIP` (`pkg/lib/oauth/handler/ratelimit.go:32`). `GetRateLimits()` is always non-nil at request time.

Despite the spec's rationale for the per-IP bucket ("one caller spreading abuse across many different projects"), it is per (app, IP), not global: `Limiter` prefixes with the app id unless `IsGlobal` is set, and every existing per-IP bucket in the codebase (`SignupPerIP`, `OAuthTokenPerIP`, `OAuthRegisterPerIP`) is per-app. A single global bucket would let one project's traffic rate-limit an unrelated project's users behind the same NAT egress — cross-tenant availability coupling that is worse than the gap it closes. See §6 D2 and the spec update in §5.

Bucket arguments need no hashing: `BucketSpec.Key()` (`pkg/lib/ratelimit/bucket.go:69-71`) joins with `:`, and an IP address cannot contain one. Dropping the per-host bucket removes the only argument that was an attacker-supplied string, so the key-collision question disappears with it.

### 3.2 `RateLimiter` — the `ServiceRateLimiter` implementation

```go
type Limiter interface {
	Allow(ctx context.Context, spec ratelimit.BucketSpec) (*ratelimit.FailedReservation, error)
}

type RateLimiter struct {
	Limiter            Limiter
	RemoteIP           httputil.RemoteIP
	OAuthFeatureConfig *config.OAuthFeatureConfig
}

func (r *RateLimiter) CheckFetchAllowed(ctx context.Context) error {
	rateLimits := r.OAuthFeatureConfig.GetClientIDMetadataDocument().GetRateLimits()
	specs := []ratelimit.BucketSpec{
		NewBucketSpecCIMDFetchPerIP(rateLimits, string(r.RemoteIP)),
		NewBucketSpecCIMDFetchPerProject(rateLimits),
	}
	for _, spec := range specs {
		failed, err := r.Limiter.Allow(ctx, spec)
		if err != nil {
			return err
		}
		if err := failed.Error(); err != nil {
			return err
		}
	}
	return nil
}
```

Neither bucket needs the target host, so `CheckFetchAllowed` takes only a `ctx` — Part 3's `ServiceRateLimiter` interface drops the `host` parameter with it. If the global per-host bucket in §1.1 is ever built, it can be added back then, against a real caller.

Ordering is per-IP then per-project. It does not change *whether* a request is refused — both are consumed on every allowed attempt — only which bucket is debited when one refuses, since the first failure short-circuits. Checking the caller-scoped bucket first means a single abusive caller is stopped without debiting the shared project bucket, so it cannot deny service to the project's legitimate CIMD clients. Same convention as `RegistrationHandler.Handle` and `docs/specs/rate-limit.md`.

Both are consumed on **every** attempt, successful or not — deliberately unlike credential-verification limits, which take a token only on failure. The resource being protected is the outbound request itself, so a successful fetch must count: an attacker pointing Authgear at a victim gets exactly the responses they wanted from a stream of successes.

`CheckFetchAllowed` returns the raw `ratelimit` error; Part 3 §6.3 maps `apierrors.IsKind(err, ratelimit.RateLimited)` to `x_rate_limited`. `pkg/lib/cimd` does not import `pkg/lib/oauth/protocol`.

`httputil.RemoteIP` is request-scoped and already in the auth server's graph (`RegistrationHandler` takes it the same way, `handler_register.go:51`). `cimd.Service` is only ever constructed per request, so this is safe — but confirm during wiring: in a graph without a request, `RemoteIP` is empty and the per-IP bucket degenerates into a second shared bucket.

### 3.3 Where it is consumed

Nothing changes in `cimd.Service.EnsureClientResolved` — Part 3 §3.3 already calls `s.RateLimiter.CheckFetchAllowed(ctx)` at step (6), between single-flight acquisition and the fetch. This part only swaps the binding.

Two properties of that position, both load-bearing:

- **After the freshness check**, so a warm, fresh CIMD client consumes nothing. This is what makes 5/minute per IP viable at all (§1.2): a project with 50 popular CIMD clients performs at most 50 fetches per *hour*. If the limits were consumed per `/oauth2/authorize` request instead, a single busy client would keep every bucket permanently empty.
- **After single-flight acquisition**, so a stampede of concurrent requests for one stale client debits one token, not N.

## 4. Residual risk — bounded, with a lever

**A determined attacker can still make a project's CIMD onboarding unusable.** 10 fetches/minute per project is a shared bucket; an unauthenticated caller sending novel `client_id` URLs keeps it empty, and every legitimate new-or-stale CIMD client in that project then fails to resolve for as long as the attack continues.

This is not fixable with tighter numbers — any per-project ceiling low enough to make the attack expensive is also low enough to throttle a legitimate project, and outbound requests to arbitrary third parties genuinely must have a per-project ceiling. What bounds the damage:

- Already-resolved, fresh clients are **unaffected** — they never reach the limiter (§3.3). An attack degrades *new* client onboarding and *refreshes*, not existing sessions or existing clients' logins.
- `/oauth2/token` never fetches, so no in-flight authorization or refresh breaks when a bucket is empty.
- A project that does not need CIMD leaves `enabled: false` (the default), and the whole path including the limiter is unreachable.
- A project that needs CIMD only from known domains sets `allowed_domains`, checked **before** the limiter (Part 3 §3.3 step 3): a novel-URL flood from a non-allowlisted host is refused for free and debits nothing. For any deployment that is not the open MCP use case, this turns the risk into a non-issue. It works here precisely because it is a fetch-path check, and it does so without affecting any already-resolved client (Part 1 §4.1).
- **The operator now has a lever.** Unlike the fixed-limit design this part started from, an operator can raise a plan tier's `per_project` burst — or disable a bucket outright — during an incident, without a code change or a release. That is the main practical argument for §1.3.

Compare DCR's analogous note (`docs/plans/dcr/2026-08-17-02-client-registration.md` §5.1.1): there the damage was quota exhaustion needing a human to clear it. Here the attack is purely transient — it stops when the traffic stops, and the buckets refill. Say so in the PR, so this section is not read as a regression.

`ratelimit.Limiter` already dispatches a non-blocking event on a failed reservation, so `oauth.cimd_fetch.*` appears in the existing rate-limit telemetry with no extra work. Confirm while implementing (`pkg/lib/ratelimit/limiter.go`'s `EventService`) and mention it in the PR.

## 5. Spec Updates

`doc:` commit against `docs/specs/cimd.md` § Denial of Service — this part deviates from that section in three ways, so it needs a real rewrite rather than a tweak:

1. **Drop the per-(project, host) bucket** from the table, with a one-line note on why: per-project already caps harm to any single victim, and a per-project host bucket never limited the aggregate case that matters. Mention that a **global** per-host bucket is the shape to reach for if victim-oriented limiting is ever needed. (§1.1)
2. **Per caller IP becomes 5/minute**, and the rationale changes: the limits count *fetches*, and fetches are deduplicated per `client_id` and per refetch interval, so legitimate per-IP fetch volume is near zero regardless of how many users sit behind one NAT. (§1.2)
3. **The limits are configurable in `authgear.features.yaml`**, not fixed. Replace "Fixed limits, not project-configurable" with something precise: not *project*-configurable — `authgear.yaml` cannot set them and a tenant admin cannot raise them — but tunable per plan tier through the Site Admin surface, because the operator owns the egress reputation and needs a lever during an incident. Document the defaults (10/min per project, 5/min per (project, IP)) as defaults rather than constants. (§1.3)
4. **The per-IP bucket is per (project, IP), not global.** Correct the "one caller spreading abuse across many different projects" rationale: as built, it bounds one caller *within* one project. A global bucket is rejected because it would let one project's traffic rate-limit an unrelated project's users behind the same NAT egress — see §6 D2.
5. **Limits are consumed per fetch attempt, not per authorization request** (also listed in Part 3 §8; whichever lands first makes the edit).
6. **§ Domain Trust**: add that `allowed_domains` short-circuits before the limiter, making it the effective mitigation for §4's residual risk.

## 6. Fixed Behavioral Decisions

- **D1. The rates are configurable in `authgear.features.yaml`, and only there.** Site-Admin-only, so no tenant can raise its own ceiling; the operator can, and needs to (§1.3). Deliberately asymmetric with DCR's `authgear.yaml` rate limits, because DCR load lands on Authgear's database and CIMD load lands on a third party's server.
- **D2. The per-IP bucket is per (project, IP).** A global bucket would create cross-tenant availability coupling for NATed callers; every existing per-IP bucket in the codebase is per-project. Spec text corrected.
- **D3. There is no per-(project, host) bucket.** §1.1. If victim-oriented limiting is wanted, it must be a global per-host bucket, decided on its own merits.
- **D4. Per-IP defaults to 5/minute, tighter than per-project's 10.** §1.2. This is only viable because buckets count fetches, not requests — so it also depends on D5.
- **D5. Buckets are consumed only when a fetch is actually about to happen** — after the freshness check and after single-flight acquisition. Moving the limiter earlier would break D4.
- **D6. Both buckets are consumed on every fetch attempt, success or failure.** The protected resource is the outbound request.
- **D7. Order is per-IP → per-project**, so an abusive caller cannot drain the shared project bucket on its way to being refused.
- **D8. `rate_limits` merges whole-bucket, not field-wise.** `enabled`/`period`/`burst` are one unit; merging them field-wise would let two layers produce a bucket neither wrote.
- **D9. Bucket specs live in `pkg/lib/cimd`, not `pkg/lib/oauth/handler`.** Keeps `cimd` from importing `handler`.
- **D10. `CheckFetchAllowed` returns the raw `ratelimit` error.** Protocol-level mapping stays in `handler_authz.go` (Part 3 §6.3).
- **D11. A rate-limited resolution reports `x_rate_limited`, not the uniform unresolvable error.** Accepted as distinguishable: folding it into the uniform error would make a throttled client indistinguishable from a broken document for a legitimate developer, and would let an attacker silently deny a competitor's client with no operator signal. Consistent with `/oauth2/token` and `/oauth2/register`. Dropping the per-host bucket also removes the one residual inference the earlier draft had to accept here ("this project recently fetched this host").
- **D12. `CheckFetchAllowed` takes no `host` parameter.** Dropping the per-host bucket left nothing that reads it, and a parameter kept for a hypothetical future caller is dead weight that misleads the next reader about what the function depends on.

## 7. Test Plan

**Unit — `pkg/lib/config` (feature config) — mandatory per the `update-feature-config` skill**

`pkg/lib/config/testdata/merge_feature.yaml`:

- a layer setting `oauth.client_id_metadata_document.rate_limits.per_project`, asserting the merged result keeps it **and** keeps `insecure_*` flags and `oauth.client` fields set by other layers — this is what catches a `Merge` that replaces `OAuthClientIDMetadataDocumentFeatureConfig` wholesale;
- a layer setting only `per_ip`, asserting `per_project` is untouched;
- a later layer overriding `per_ip`, asserting whole-bucket replacement (all three of `enabled`/`period`/`burst` come from the later layer, even the ones it omitted);
- a later layer omitting `rate_limits` entirely, asserting an earlier layer's buckets survive;
- after defaults, absent config yields `per_project` 10/1m and `per_ip` 5/1m — and **not** the values from any test fixture.

Schema: `burst: 0` fails (`minimum: 1`); `enabled: true` without `period` fails (`RateLimitConfig`'s own `if/then`); an unknown key under `rate_limits` fails.

**Unit — `pkg/lib/cimd/ratelimit_test.go` (new)**

With a stub `Limiter` recording every spec passed to `Allow`:

- both specs are requested, in the order per-IP → per-project, and **only** two — assert the count, which is the regression guard against the per-host bucket being reinstated;
- each spec carries the expected `RateLimitName`, `RateLimitGroup`, `BucketName`, and the `Enabled`/`Period`/`Burst` **from the supplied feature config**, not from a literal;
- the per-IP spec's single argument is the `RemoteIP`; the per-project spec has no arguments;
- a `FailedReservation` on the per-IP spec short-circuits: the per-project `Allow` never happens;
- `per_ip.enabled: false` → that spec is passed with `Enabled: false` (the limiter itself short-circuits, so `Allow` is still called — assert the spec, not the absence of the call);
- a transport error from `Allow` is returned unchanged.

**Unit — `pkg/lib/cimd/service_test.go` (extend Part 3's file)**

- fresh record → `CheckFetchAllowed` **never called** (D4, and the most likely regression: someone "simplifies" by moving the limiter to the top of the function);
- single-flight not acquired → `CheckFetchAllowed` **never called**;
- `allowed_domains` refusal → `CheckFetchAllowed` **never called**;
- `CheckFetchAllowed` returns a `ratelimit.RateLimited` error → `EnsureClientResolved` returns it unchanged (not `ErrUnresolvable`), and the fetcher is never called;
- `CheckFetchAllowed` returns a rate-limit error while a **stale record exists** → the error is still returned, i.e. rate limiting does **not** fall back to serving stale. Rationale: the stale fallback in Part 3 §5 is for "the client's server let us down", whereas a rate-limited request means Authgear declined to try; masking that as success would hide the throttle from the operator and, worse, would let an attacker keep a project's clients permanently on stale metadata for free. Make this an explicit assertion so nobody "fixes" it later.

**Unit — `pkg/lib/oauth/handler/handler_authz_test.go` (already covered)**

Part 3 §7 already asserts `ratelimit.RateLimited` → `x_rate_limited`. No new case.

Modelled on `e2e/tests/dcr/register_ratelimit.test.yaml`. Uses the `e2e/cmd/cimdserver` fixture host from Part 3 §7 in a project whose `authgear.features.yaml` override carries both the permissive fetch flags **and** an explicit, small rate limit — configurability is what makes this test easy to write, so use it rather than sending dozens of requests:
