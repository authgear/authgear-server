# CIMD Part 7 — Serving `logo_uri` Through Authgear Instead of the User's Browser

Spec: [docs/specs/cimd.md — Privacy Considerations §9.2](../../specs/cimd.md#privacy-considerations), [SSRF Protection §8.8](../../specs/cimd.md#ssrf-protection).

Depends on [Part 2](2026-08-28-02-document-fetching.md) (`SafeDialer`, `IsPubliclyRoutable`, `CIMDHTTPClients`, `clientFor`) and [Part 6](2026-08-28-06-consent-and-authorized-apps.md) (the consent screen's `<img>` and `ConsentViewModel.ClientLogoURI`).

## 1. Goal / Scope

Part 6 renders a CIMD client's `logo_uri` directly, so the end user's browser fetches the image from the client's own server. Spec § Privacy Considerations §9.2 describes exactly why that is a problem:

> if Authgear rendered `logo_uri` directly in the end user's browser, that browser would fetch it straight from the client's own server, leaking the user's IP and browser fingerprint to that third party as a side effect of merely viewing a consent screen — a tracking-pixel-shaped risk.

This part closes it. The end user's browser only ever talks to Authgear; Authgear fetches the image itself, through the same SSRF-safe transport the metadata document uses.

**Design, per the approach chosen for this work:** a **lazy proxy endpoint**, not a prefetch. Authgear does not fetch the logo when it resolves the metadata document; it fetches it the first time someone actually requests it, streams it back, and caches it.

Out of scope: `logo_uri` for **static** clients (§2.3), image resizing/transcoding, and any portal surface. DCR clients **are** covered — see §2.3.

## 2. Endpoint design

### 2.1 Route

```go
// pkg/auth/handler/webapp/client_logo.go  (new)

func ConfigureClientLogoRoute(route httproute.Route) httproute.Route {
	return route.
		WithMethods("GET", "HEAD", "OPTIONS").
		WithPathPattern("/_internals/client_logo")
}
```

`/_internals/client_logo?client_id=<url-encoded client_id>`.

**Not under `/oauth2/`.** That prefix is reserved for endpoints defined by an OAuth specification; this one is an Authgear convenience with no spec behind it. `/_internals/` is the established prefix for Authgear-specific, browser-reachable endpoints in the auth server — `_internals/ws`, `_internals/oauth_entrypoint`, `_internals/passkey/creation_options`, `_internals/passkey/request_options` — and the underscore spelling matches them.

Two consequences of the prefix, both worth following rather than fighting:

- **The handler belongs in `pkg/auth/handler/webapp/`, not `pkg/auth/handler/oauth/`.** Every existing `_internals` handler lives there. It is browser-facing, not protocol-facing.
- **Register it on `webappAPIRoute`** (`pkg/auth/routes.go:304`, whose chain is the bare `webappChain`), the same minimal chain the passkey-options endpoints use. It must not go on a page or authenticated chain: the logo is fetched by an `<img>` on the consent screen, with no session and no CSRF token.

**Why `client_id` in the query and not the logo URL itself.** The obvious shape — `/logo?url=https://…` — is an open proxy: anyone could make Authgear fetch any URL and stream the bytes back to them, which is a strictly worse SSRF surface than the metadata fetch (the response body comes back to the attacker instead of being validated and discarded). Keying on `client_id` means the only URLs this endpoint can ever fetch are ones that appeared in a `logo_uri` of an already-persisted, already-validated CIMD document. The attacker's control is reduced to "whatever I can get into a document I host", and that document had to pass the Part 2 validation and the Part 3/4/5 gates to be persisted at all.

**Why not a path parameter keyed on the row `id`.** The row uuid would be a shorter, opaque key. Rejected: the consent screen has a `*config.OAuthClientConfig`, which carries `ClientID` but not the row uuid, so using the uuid would mean threading it through `ToClientConfig` for this one purpose. `client_id` is already there.

### 2.2 Handler flow

```go
type ClientLogoHandler struct {
	// Resolver is a plain read; oauthclient.Queries opens its own database
	// scope when it needs one, so this handler needs no *appdb.Handle.
	Resolver ClientLogoClientResolver // ResolveClient(ctx, clientID) *config.OAuthClientConfig
	Logos    *cimd.LogoService
}

func (h *ClientLogoHandler) ServeHTTP(rw http.ResponseWriter, r *http.Request) {
	clientID := r.URL.Query().Get("client_id")

	// (1) Resolve the client. This is a plain read -- Redis, then Postgres.
	// It does NOT go through cimd.Service.EnsureClientResolved: this endpoint
	// must never trigger a metadata document fetch (Part 3 D1, spec § Where
	// resolution happens -- "any outbound network call happens ONLY as a side
	// effect of /oauth2/authorize"). A client_id with no persisted record is
	// simply a 404 here.
	client := h.Resolver.ResolveClient(r.Context(), clientID)
	if client == nil || client.LogoURI == "" {
		http.NotFound(rw, r)
		return
	}

	// (2) Dynamic clients only -- DCR and CIMD both have self-asserted
	// logo_uri. A static client's is admin-configured and already rendered
	// directly by __brand_logo.html. See §2.3.
	if !client.IsDynamicClient() {
		http.NotFound(rw, r)
		return
	}

	// (3) Serve from cache, or fetch-and-cache. §3.
	result, err := h.Logos.Get(r.Context(), clientID, client.LogoURI)
	if err != nil {
		// Every logo-specific failure collapses to one Kind and one 404, so
		// the endpoint cannot report on the reachability of whatever host the
		// document named (§3.4). An infrastructure failure is NOT that Kind
		// and must not be swallowed as a 404.
		if apierrors.IsKind(err, cimd.CIMDLogoUnavailable) {
			http.NotFound(rw, r)
			return
		}
		logger := ClientLogoHandlerLogger.GetLogger(r.Context())
		logger.WithError(err).Error(r.Context(), "failed to serve client logo")
		http.Error(rw, "Internal Server Error", http.StatusInternalServerError)
		return
	}

	rw.Header().Set("Content-Type", result.ContentType)
	rw.Header().Set("Content-Length", strconv.Itoa(len(result.Body)))
	// Not "no-store": the whole point is that browsers stop re-fetching.
	// private, because the response is not user-specific but is served on a
	// path that may sit behind a per-tenant CDN; keep it out of shared caches
	// to avoid one project's logo being served for another's host.
	rw.Header().Set("Cache-Control", "private, max-age=3600")
	rw.Header().Set("X-Content-Type-Options", "nosniff")
	// The image is attacker-supplied bytes served from Authgear's own origin.
	// Both headers below are what prevent that from being an XSS vector; see
	// §4.
	rw.Header().Set("Content-Disposition", "inline")
	rw.Header().Set("Content-Security-Policy", "default-src 'none'; sandbox")
	http.ServeContent(rw, r, "", result.FetchedAt, bytes.NewReader(result.Body))
}
```

`http.ServeContent` rather than `rw.Write` gives conditional-request handling (`If-Modified-Since`, `If-None-Match` via the `Last-Modified` it derives) and range support for free, the same reason `httputil.FilesystemCache` exists.

### 2.3 Which clients the proxy covers: both dynamic sources, not static

A static client's `logo_uri` is chosen by the project admin, and the existing `__brand_logo.html` renders it directly when `ReplaceProjectLogoWithLogoURI` is set. Routing that through a proxy would change behavior for existing projects (caching, CSP, image formats) with no privacy benefit — spec §9.2's threat is a *third party the user has no relationship with* learning the user's IP, and a project's own logo host is not that.

**A DCR client's `logo_uri` is proxied too, and must be.** It is self-asserted exactly like a CIMD client's, and Part 6 §2.4's `<img>` is populated from `Client.LogoURI` for *any* client — so after Part 6 a DCR client's logo renders on the consent screen and leaks the end user's IP to the DCR client's host. Covering only CIMD would leave that open while claiming the §9.2 risk was addressed. The gate is therefore `IsDynamicClient()`, not `IsCIMDClient()`:

```go
	if !client.IsDynamicClient() {
		http.NotFound(rw, r)
		return
	}
```

`IsDynamicClient()` is true for both `source: DCR` and `source: CIMD` and false for every static client (Part 1 §5.1), so this one predicate expresses "self-asserted metadata" exactly.

## 3. Caching — and why not a local file cache

The user-facing requirement is that the consent screen not make a 5-second outbound fetch on every render. So the fetched bytes must be cached somewhere.

### 3.1 Assessment of the local-file-cache option

`pkg/util/httputil/FilesystemCache` exists and writes to `os.TempDir()`. **It is not safe for this use**, for four reasons:

1. **No eviction, no TTL, no size bound.** `FilesystemCache` has `Clear()` and nothing else — entries live until the process clears them all. Its existing users cache a fixed, small set of generated static assets. Here the key space is attacker-influenced: a `client_id` is a URL, and an attacker who can host documents can mint unbounded distinct `client_id`s (Part 4's limits slow this but do not bound the total, and each one legitimately reaches quota only if it resolves — but `logo_uri` values *within* one client's documents can also change on every refetch). Unbounded writes to `os.TempDir()` is a disk-exhaustion path.
2. **Per-pod, so the cache hit rate collapses under horizontal scaling** and each pod independently re-fetches. For a 4-pod deployment that is 4× the outbound requests and 4× the leak-to-the-client's-server signal that §9.1 asks us to reduce.
3. **`FilesystemCache.Serve` is keyed on `r.URL.Path`** via `filepathutil.EscapePath`, and this endpoint's key is in the *query string*. Using it would mean either moving `client_id` into the path (where it needs escaping of an arbitrary URL — a path-traversal surface) or reworking the cache's keying.
4. **It writes with mode `0666`** and no per-tenant separation. On a shared host that is a cross-tenant read of one project's cached bytes; benign for a public logo, but it is not a property to introduce deliberately.

None of these is fatal in isolation; together they mean adopting it would require rewriting it, at which point it is not a reuse.

### 3.2 Recommendation: Redis, with a hard size cap

```go
// pkg/lib/cimd/logo.go (new)

const (
	// MaxLogoBytes bounds both the fetch and the cache entry. 256 KiB is
	// generous for a consent-screen logo (the document itself is capped at
	// 5 KiB) and small enough that a full cache of them is a bounded, sane
	// Redis footprint: even at the Part 5 quota's scale, N clients x 256 KiB
	// is megabytes, not gigabytes.
	MaxLogoBytes = 256 * 1024

	// logoCacheTTL. One hour matches cimd.RefetchInterval, so a client that
	// changes its logo_uri sees the change take effect on roughly the same
	// timescale as any other metadata change.
	logoCacheTTL = 1 * time.Hour

	// logoNegativeCacheTTL. A failed logo fetch IS negatively cached, unlike a
	// failed document fetch (Part 3 §4.4). The reasoning differs because the
	// consequence differs: a failed document fetch makes a client unusable, so
	// spec § Error Handling requires immediate retry; a failed logo fetch
	// costs a missing image, and retrying it on every consent-screen render
	// would be a free amplifier pointed at whatever host the document named.
	logoNegativeCacheTTL = 10 * time.Minute
)
```

Redis is the right store here because:

- **Shared across pods**, so N pods perform one fetch, not N — directly serving spec §9.1's "reduce how often this signal is generated".
- **TTL is native**, so eviction is not something this code has to implement or get wrong.
- **`appredis.Handle` is already per-app**, so keys are tenant-scoped by construction, the same way `oauthclient.ClientCache` is.
- The size cap makes the memory cost calculable and bounded.

Key: `app:<appID>:cimd-logo:<sha256(clientID)>`, hashed for the same reason `redisKeyDynamicClient` hashes it (`cache_client.go:898-907`) — the `client_id` is an attacker-influenced URL containing `:`.

Payload: a small JSON envelope, not raw bytes, because the `Content-Type` and the fetch timestamp have to survive the round trip, and a negative entry needs to be representable:

```go
type cachedLogo struct {
	Found       bool      `json:"found"`
	ContentType string    `json:"content_type,omitempty"`
	FetchedAt   time.Time `json:"fetched_at,omitempty"`
	Body        []byte    `json:"body,omitempty"` // base64 in JSON
	// SourceURI is stored so a logo_uri change on refetch invalidates
	// implicitly: Get compares the caller's logo_uri against this and treats
	// a mismatch as a miss. Without it, a client that changed its logo would
	// keep serving the old image for up to logoCacheTTL after the document
	// refetch already landed.
	SourceURI string `json:"source_uri,omitempty"`
}
```

Base64 inflates the payload by ~33%; at a 256 KiB cap that is ~341 KiB per entry, still fine. If that is judged wasteful, store the body under a second raw key and the metadata under the JSON key — but do not do that without a measured reason.

**Rejected alternative: `pkg/lib/cloudstorage`.** It exists (S3/GCS/Azure/MinIO/OSS) and `pkg/images` uses it. Rejected because it is durable storage with no TTL — every cached logo would need an explicit lifecycle policy or a cleanup job, and the auth server does not currently have a `cloudstorage` dependency at all (only `pkg/images`, `pkg/portal` and `pkg/lib/userexport` do). Adding one for a cache that Redis handles with a TTL is a large dependency for a small gain.

### 3.3 `LogoService`

```go
type LogoService struct {
	Redis   *appredis.Handle
	AppID   config.AppID
	Clock   clock.Clock
	Fetcher *LogoFetcher
	SingleFlight *FetchSingleFlight // reused from Part 3 §4.3, different key prefix
}

type LogoResult struct {
	ContentType string
	Body        []byte
	FetchedAt   time.Time
}

// Get returns the cached logo, fetching it on a miss.
//
// logoURI comes from the caller's already-resolved client config, so it has
// already been validated as https:// by cimd.ParseAndValidate. Get
// re-validates it anyway (§4) rather than trusting the caller: this function
// is what turns a string into an outbound request, and the check belongs
// where the request is made.
func (s *LogoService) Get(ctx context.Context, clientID string, logoURI string) (*LogoResult, error)
```

Flow:

1. Redis `GET`. Hit with `Found: true` and `SourceURI == logoURI` → return it. Hit with `Found: false` and matching `SourceURI` → return `ErrLogoNegativeCached` (negative cache). Hit with a different `SourceURI` → treat as a miss.
2. Single-flight `Acquire` on a `cimd-logo-fetch:` key. Not acquired → return `ErrLogoFetchInFlight` (the image is simply missing for this render; the next one will hit the cache the winner populated). Reusing `FetchSingleFlight` with a distinct key prefix means one implementation and one TTL constant.
3. Fetch (§4).
4. On success, `SET` the positive entry with `logoCacheTTL` and return it. On failure, `SET` the negative entry with `logoNegativeCacheTTL` and return the fetch error unchanged.

A Redis failure at step 1 or 4 must not fail the request — fall through to a fetch, and ignore a failed `SET`. Same posture as `Queries.getClientByClientIDCached` (`queries.go:378-384`).

### 3.4 Errors — one Kind at the service boundary

Same split as [Part 3](2026-08-28-03-authorize-time-resolution.md) §3.2, for the same reasons:

```go
// CIMDLogoUnavailable covers every logo-specific failure: fetch error,
// non-2xx, oversize, disallowed or mismatched content type, invalid
// logo_uri, negative cache hit, a fetch already in flight, and a
// rate-limit refusal. One Kind, one reason -- the endpoint must not report
// on the reachability of the host the document named.
var CIMDLogoUnavailable = apierrors.NotFound.WithReason("CIMDLogoUnavailable")

func ErrLogoUnavailable() error {
	return CIMDLogoUnavailable.New("client logo is unavailable")
}
```

- **`LogoFetcher` keeps its specific sentinels** (`ErrLogoInvalidURI`, `ErrLogoContentType`, `ErrLogoContentMismatch`, `ErrLogoTooLarge`, plus `ErrResponseNotOK`/`ErrResponseTooLarge` from Part 2) so its tests assert which rule fired.
- **`LogoService.Get` is the collapse boundary.** It logs the concrete cause and returns `CIMDLogoUnavailable` for every logo-specific failure — including a `ratelimit.RateLimited` refusal, deliberately (§4.1) — and passes anything else through unchanged.
- **An infrastructure error is not `CIMDLogoUnavailable`.** A Redis or Postgres failure returns as itself, so the handler renders a 500 and it reaches error monitoring. A blanket `if err != nil { 404 }` — what an earlier draft of this part specified — would silently turn a Redis outage into "this client has no logo", which is exactly the class of bug the Part 3 D11 rule exists to prevent.
- **Never `NewWithCause`/`NewWithInfo`.** `Details` is rendered into the response body; the cause is logged, never attached.

`apierrors.NotFound` is chosen so the `Name`'s own HTTP status (404) already matches what the handler writes.

## 4. Fetching an image safely

`cimd.Fetcher` (Part 2 §2.5) is document-specific: it sends `Accept: application/json` and enforces `MaxDocumentBytes`. Add a sibling rather than parameterising it, so neither can drift into the other's limits:

```go
// pkg/lib/cimd/logo_fetcher.go

// LogoFetcher reuses the document fetch's clients and its client-selection
// rule verbatim -- same SafeDialer, same strict/insecure pair (Part 2 §2.5,
// §2.5.1), same insecure_fetch_address_allowed feature flag (Part 1 §2.4).
// A logo fetch that used the strict client while the document fetch used the
// permissive one would make a project's own logo unfetchable in exactly the
// environments the flag exists for; the reverse would be a policy hole.
type LogoFetcher struct {
	HTTPClients        *CIMDHTTPClients
	OAuthFeatureConfig *config.OAuthFeatureConfig
	AppID              config.AppID
}

var (
	ErrLogoNegativeCached  = errors.New("cimd: logo fetch previously failed")
	ErrLogoFetchInFlight   = errors.New("cimd: a logo fetch is already in flight")
	ErrLogoInvalidURI      = errors.New("cimd: invalid logo_uri")
	ErrLogoContentType     = errors.New("cimd: unsupported logo content type")
	ErrLogoContentMismatch = errors.New("cimd: logo content does not match an allowed image type")
	ErrLogoTooLarge        = errors.New("cimd: logo exceeds the maximum size")
)

var allowedLogoContentTypes = map[string]bool{
	"image/png":     true,
	"image/jpeg":    true,
	"image/gif":     true,
	"image/webp":    true,
	// image/svg+xml is DELIBERATELY absent. An SVG is a document, not an
	// image: it can contain <script>, external references and CSS, and it is
	// attacker-supplied content that would be served from Authgear's own
	// origin. The CSP + sandbox headers in §2.2 defend against this, but
	// defence in depth means not accepting the format at all. A client that
	// wants a logo shown ships a raster image.
	// image/x-icon and image/vnd.microsoft.icon are also absent -- no reason
	// to accept a format nothing needs.
}

func (f *LogoFetcher) Fetch(ctx context.Context, logoURI string) (body []byte, contentType string, err error) {
	// Re-validate the scheme and shape at the point of use, not just at
	// document-validation time. The rules from spec § SSRF Protection ("The
	// same rules apply to fetching logo_uri") come for free via the shared
	// SafeDialer: address filtering, DNS pinning, 0 redirects, the 5s
	// timeout. Only the size limit and the content type are specific to this
	// fetch.
	//
	// https, unless insecure_http_allowed is set for this project (Part 1
	// §2.4, D13a) -- the same flag and the same posture that let the document
	// itself declare a http logo_uri (Part 2 §3 rule 8). The two MUST agree:
	// if validation stored a http logo_uri and this refused to fetch it, a
	// test project's logo would be permanently 404, which is exactly the
	// e2e case in §6.
	//
	// Note this is the ONLY relaxation here. The content-type allowlist, the
	// SVG exclusion, the byte cap and the sniffed-type agreement check below
	// all still apply, and the address filter still applies through clientFor.
	u, err := url.Parse(logoURI)
	allowHTTP := f.OAuthFeatureConfig.GetClientIDMetadataDocument().IsInsecureHTTPAllowed()
	schemeOK := err == nil && (strings.EqualFold(u.Scheme, "https") ||
		(allowHTTP && strings.EqualFold(u.Scheme, "http")))
	if !schemeOK || u.Host == "" {
		return nil, "", ErrLogoInvalidURI
	}

	req, err := http.NewRequestWithContext(ctx, http.MethodGet, u.String(), nil)
	// Accept only what we will serve, so a well-behaved server does not send
	// us a 20 MB TIFF we then discard.
	req.Header.Set("Accept", "image/png, image/jpeg, image/gif, image/webp")
	req.Header.Set("User-Agent", "Authgear")

	resp, err := f.clientFor(ctx, u).Do(req)
	// ... 2xx check, identical to Fetcher.Fetch

	// Content-Type from the server, normalized: strip parameters and
	// lowercase, then check the allowlist. mime.ParseMediaType handles
	// "image/png; charset=utf-8" and rejects garbage.
	mediaType, _, err := mime.ParseMediaType(resp.Header.Get("Content-Type"))
	if err != nil || !allowedLogoContentTypes[strings.ToLower(mediaType)] {
		return nil, "", ErrLogoContentType
	}

	// Progressive size enforcement, same +1 trick as the document fetch.
	// Content-Length is not trusted.
	body, err = io.ReadAll(io.LimitReader(resp.Body, MaxLogoBytes+1))
	if err != nil {
		return nil, "", err
	}
	if len(body) > MaxLogoBytes {
		return nil, "", ErrLogoTooLarge
	}

	// Sniff the bytes and require agreement with the declared type. A server
	// can lie in Content-Type; the bytes are what a browser will act on.
	// http.DetectContentType reads at most 512 bytes and returns one of a
	// fixed set including the four image types above.
	sniffed, _, err := mime.ParseMediaType(http.DetectContentType(body))
	if err != nil || !allowedLogoContentTypes[strings.ToLower(sniffed)] {
		return nil, "", ErrLogoContentMismatch
	}

	// Serve the SNIFFED type, not the declared one. The header we send is
	// what the browser trusts, so it must be derived from the bytes.
	return body, sniffed, nil
}
```

The declared-type check and the sniffed-type check are both present on purpose: the declared type lets a compliant server be rejected cheaply before the body is read, and the sniffed type is what actually governs what the browser does. Only the sniffed type is echoed back.

### 4.1 Rate limiting the logo fetch — one fixed bucket, per client_id

**Fixed, not configurable, and keyed per `client_id`.** An earlier draft mirrored [Part 4](2026-08-28-04-rate-limits.md)'s per-project and per-IP buckets and made them configurable. That was the wrong shape, because the logo path is already bounded from two directions that the document fetch is not:

- **A logo fetch requires a persisted client record.** Records are only created or refreshed by a document fetch, which Part 4 already limits per project and per IP, and their total is capped by the `oauth_client_cimd` quota ([Part 5](2026-08-28-05-usage-limit.md)). So the number of distinct logos that can be fetched at all is already governed by the document-fetch limits — a per-project logo bucket would re-limit the same population a second time.
- **The cache bounds repeat fetches per logo.** A positive entry lives an hour, a negative entry ten minutes, and concurrent misses collapse through single-flight (§3.3). So the steady-state ceiling for one client is already about 6 fetches/hour with no limiter at all.

What that leaves unbounded is the one case the cache cannot cover: repeated misses for a *single* client, if cache writes are failing or being evicted. That is a per-`client_id` concern, so it wants a per-`client_id` bucket and nothing else:

```go
// pkg/lib/ratelimit/ratelimits.go
RateLimitGroupOAuthCIMDLogo RateLimitGroup = "oauth.cimd_logo"
RateLimitOAuthCIMDLogoPerClient RateLimitName = "oauth.cimd_logo.per_client"
OAuthCIMDLogoPerClient BucketName = "OAuthCIMDLogoPerClient"
```

```go
// pkg/lib/cimd/logo.go
func NewBucketSpecCIMDLogoPerClient(clientID string) ratelimit.BucketSpec {
	// The client_id is hashed, unlike Part 4's IP argument. BucketSpec.Key()
	// joins arguments with ":" (pkg/lib/ratelimit/bucket.go:69-71) and a
	// client_id is a URL containing ":", so passing it raw would let one
	// client_id's key collide with another's namespace -- the same reason
	// redisKeyDynamicClient hashes it (cache_client.go:898-907).
	return ratelimit.NewBucketSpec(
		ratelimit.RateLimitOAuthCIMDLogoPerClient,
		ratelimit.RateLimitGroupOAuthCIMDLogo,
		&config.RateLimitConfig{Enabled: new(true), Period: "1m", Burst: 2},
		ratelimit.OAuthCIMDLogoPerClient,
		crypto.SHA256String(clientID),
	)
}
```

The bucket is per (app, client_id): `BucketSpec.IsGlobal` is false, so `Limiter` prefixes with the app id.

**Burst 2 per minute is deliberately strict.** A legitimate cache miss needs exactly one fetch, and the negative cache then suppresses retries for ten minutes, so 2/minute already allows a retry that legitimate traffic never needs. The cost of being wrong is a missing image on a consent screen, not a blocked login — so the tradeoff sits much further toward strictness than the document fetch's does.

**Not configurable**, unlike Part 4's document-fetch limits. The argument that made those configurable was that an operator needs a lever when a legitimate high-volume project is throttled and onboarding breaks. Neither half applies here: legitimate per-client logo volume is a constant (one fetch per cache lifetime, regardless of traffic), and the failure mode is cosmetic. A knob nobody has a reason to turn is a knob that only adds surface.

It also means Part 4 §2's `rate_limits` config gains **nothing** for logos — do not add `logo_per_project`/`logo_per_ip` fields there.

**Its own group**, `oauth.cimd_logo`, so logo traffic can never consume the document fetch's allowance — document resolution is the more important of the two. The group name tracks the subsystem, not the route, so it is unaffected by the endpoint moving out of `/oauth2/` (§2.1).

Consumed **only on a cache miss that is about to fetch** — after the cache read and after single-flight acquisition, exactly as in Part 4 §3.3.

A rate-limited logo fetch collapses into `CIMDLogoUnavailable` → 404, and **writes no cache entry** (a throttled attempt must not poison the negative cache for ten minutes). Not a `429`: nothing renders an error for an `<img>`, so a distinguishable status would only confirm to a caller that they had reached a real client's logo.

## 5. Wiring the consent screen to the proxy

`pkg/auth/handler/oauth/consent.go`'s `renderConsentPage`, replacing Part 6 §2.2's direct assignment:

```go
	// Point the <img> at Authgear's own proxy instead of the client's server,
	// so the end user's browser never contacts the client (spec § Privacy
	// Considerations §9.2). Only for a dynamic client -- a static client's
	// logo continues to render directly, per §2.3.
	if consentRequired.Client.LogoURI != "" && consentRequired.Client.IsDynamicClient() {
		viewModel.ClientLogoURI = h.Endpoints.ClientLogoURL(consentRequired.Client.ClientID).String()
	} else {
		viewModel.ClientLogoURI = consentRequired.Client.LogoURI
	}
```

`ConsentHandler` (`consent.go:71-78`) has no `Endpoints` field today — add one, typed as a narrow interface in this package rather than depending on `oauth.EndpointsProvider` wholesale:

```go
type ConsentClientLogoEndpoint interface {
	ClientLogoURL(clientID string) *url.URL
}
```

`ClientLogoURL` is a new method on `*endpoints.Endpoints` (`pkg/lib/endpoints/endpoints.go`, alongside `RegistrationEndpointURL` at line 71) and a new entry in the `oauth.EndpointsProvider` interface (`pkg/lib/oauth/endpoints.go:5-11`). Note it is the **first** endpoint method taking an argument — every existing one is a bare `urlOf("oauth2/…")` — so it cannot use `urlOf` directly:

```go
func (e *Endpoints) ClientLogoURL(clientID string) *url.URL {
	u := e.urlOf("_internals/client_logo")
	q := url.Values{}
	q.Set("client_id", clientID)
	u.RawQuery = q.Encode()
	return u
}
```

`url.Values.Encode()` rather than string concatenation: the `client_id` contains `:` and `/` and may carry a query string of its own, all of which must be percent-encoded to survive the round trip.

Adding a method to `oauth.EndpointsProvider` means every implementation and every mock of that interface must gain it — `grep -rn "EndpointsProvider" --include=*.go pkg/` before starting, and expect `make generate` to update mocks.

The template from Part 6 §2.3 does **not change** — it already renders `{{ $.ClientLogoURI }}`. Keep `referrerpolicy="no-referrer"`: harmless now that the target is same-origin, and it means the attribute does not have to be re-added if the fallback branch above is ever hit.

`viewmodels.BaseViewModel.LogoURI` (`base.go:225`) is a separate thing — the *project's* brand logo, gated on `ReplaceProjectLogoWithLogoURI`, which is fixed `false` for every dynamic client. Do not touch it.

## 7. Fixed Behavioral Decisions

- **D1. Lazy fetch on request, not prefetch at document-resolution time.** A prefetch would add a second outbound request to `/oauth2/authorize`'s latency budget for an image most authorizations never display (a returning user with existing consent skips the consent screen entirely), and it would fetch logos for clients nobody ever sees.
- **D2. The endpoint is keyed on `client_id`, never on the logo URL.** A URL-keyed endpoint is an open proxy. The only fetchable URLs are `logo_uri` values from already-validated, already-persisted documents.
- **D2a. The route is `/_internals/client_logo`, not under `/oauth2/`.** `/oauth2/` is reserved for endpoints an OAuth specification defines; this one has no spec behind it. Handler in `pkg/auth/handler/webapp/`, registered on `webappAPIRoute` — the same minimal chain the `_internals/passkey/*` endpoints use, since an `<img>` load carries no session and no CSRF token.
- **D3. The endpoint never triggers a metadata document fetch.** Part 3 D1's "one call site" rule is absolute; an unknown `client_id` is a 404.
- **D4. Redis, not a local file cache.** §3.1 gives four independent reasons `httputil.FilesystemCache` is unsuitable: no eviction or size bound against an attacker-influenced key space, per-pod so N× the outbound requests, path-keyed while this endpoint keys on a query parameter, and mode-`0666` with no tenant separation.
- **D5. A hard 256 KiB cap on both the fetch and the cache entry**, enforced progressively, `Content-Length` untrusted.
- **D5a. `logo_uri` accepts `http://` exactly when `insecure_http_allowed` is set** (Part 1 §2.4, D13a) — the same flag that lets document validation store such a value. Validation and fetching must never disagree, or a test project's logo is permanently 404. No other logo protection is relaxed by it: the content-type allowlist, the SVG exclusion, the byte cap, the sniffed-type agreement and the address filter all still apply.
- **D6. SVG is not an accepted logo format.** It is a scriptable document served from Authgear's origin. The CSP/sandbox headers defend against it anyway; not accepting it is defence in depth.
- **D7. The served `Content-Type` is the sniffed type, not the declared one.** Both are checked; only the bytes decide what the browser is told.
- **D8. Every logo-specific failure is one `apierrors.Kind` and a uniform 404**, including rate-limited ones — opposite to Part 4 D11's `x_rate_limited` for `/oauth2/authorize`, because nothing renders an error for an `<img>` and a distinguishable response would confirm a real client's existence. **An infrastructure error is not that Kind** and renders a 500, so a Redis outage does not masquerade as "this client has no logo" (§3.4).
- **D9. A failed logo fetch IS negatively cached** (10 min), unlike a failed document fetch. A missing image is not a broken client, and retrying per consent-screen render would be an amplifier.
- **D10. `SourceURI` is stored in the cache envelope** so a `logo_uri` change invalidates implicitly on the next request rather than waiting out the TTL.
- **D11. The proxy covers DCR clients as well as CIMD**, gated on `IsDynamicClient()`. §2.3. The threat is identical — self-asserted metadata — and Part 6's `<img>` renders a DCR client's logo too, so covering only CIMD would leave that leak open while claiming the §9.2 risk was addressed.
- **D12. Static clients keep rendering their logo directly.** Admin-configured, already rendered directly elsewhere, not the §9.2 threat.
- **D13. One fixed rate-limit bucket, per (app, `client_id`), in its own group.** §4.1. Not per-project or per-IP — the document-fetch limits and the `oauth_client_cimd` quota already bound how many distinct logos exist — and not configurable, because legitimate per-client logo volume is a constant and the failure mode is cosmetic. The `client_id` argument is hashed, since it is a URL and `BucketSpec.Key()` joins with `:`.
