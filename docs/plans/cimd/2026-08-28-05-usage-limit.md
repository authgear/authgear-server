## 1. Goal / Scope

Add the `oauth_client_cimd` standing usage limit — a live cap on how many `source: CIMD` rows a project may hold at once — and enforce it at the one place a new row is created.

DCR Part 5 (`docs/plans/dcr/2026-08-17-05-client-usage-limit.md`) already built the entire standing-limit machinery: `usage.Limiter.CheckStanding` / `ReportStandingCreated`, `config.StandingFeatureUsageLimitConfig`, `FeatureUsageLimitsConfig.StandingLimits`, and `usage.ErrStandingUsageLimitExceeded`. **Nothing in `pkg/lib/usage` changes here.** This part is: one `model.UsageName` constant, one config field with its merge case and schema entry, and the enforcement wiring in `cimd.Service.upsert`.

The `oauth_client_cimd` string is *already* in both `UsageMatch` enums (`pkg/lib/config/feature_usage.go:8` and `pkg/lib/config/usage.go:22`), so a project can already write a `usage.hooks` / `usage.alerts` entry matching it. That was added in anticipation; it means an alert can be configured for a name that has no limit yet, which is harmless. This part makes the name real.

## 3. Enforcement — `cimd.Service.upsert`

Part 3 §3.4 left the shape in place; fill it in:

```go
func (s *Service) upsert(ctx context.Context, clientID string, doc *Document) error {
	// Serialize concurrent first-resolutions for this app so the
	// count-then-create sequence is atomic with respect to the quota. A
	// plain "SELECT COUNT(*) then INSERT" has a TOCTOU window that lets two
	// concurrent resolutions of two DIFFERENT new client_ids both observe a
	// count under quota and both create a row. Same helper and same
	// reasoning as POST /oauth2/register (handler_register.go:172-176);
	// the lock key is scoped per source (store_client.go:750), so a CIMD
	// resolution never serializes against a DCR registration.
	//
	// The single-flight guard in Part 3 §4.3 does NOT cover this: it is
	// per-client_id, and the race here is between two different client_ids
	// competing for the last quota slot.
	if err := s.Commands.LockForClientCount(ctx, model.OAuthClientSourceCIMD); err != nil {
		return err
	}

	clientCount, err := s.Commands.CountClientsBySource(ctx, model.OAuthClientSourceCIMD)
	if err != nil {
		return err
	}
	//nolint:gosec // G115 -- a client count cannot exceed MaxInt
	countBefore := int(clientCount)

	// The check is speculative and then re-decided by `created`, because
	// whether this resolution consumes a slot is not knowable until the
	// upsert runs: a refetch of an existing client_id must succeed even at
	// or over quota (spec § Client Limit: "A client_id that already has a
	// persisted record is unaffected regardless of the limit, since
	// resolving it again doesn't create a new one"), while a brand-new one
	// must be refused.
	//
	// Doing the upsert first and rolling back on refusal is what makes both
	// true with one round trip and no second existence query -- and the
	// existence query would be a TOCTOU hazard of its own even under the
	// advisory lock, because it would have to be a separate statement.
	// Returning a non-nil error from inside Database.WithTx rolls the
	// transaction back, so a refused creation leaves no row.
	limitErr := s.UsageLimiter.CheckStanding(ctx, model.UsageNameOAuthClientCIMD, countBefore)

	client, created, err := s.Commands.UpsertCIMDClient(ctx, &oauthclient.UpsertCIMDClientOptions{
		ClientID:        clientID,
		ApplicationType: doc.ApplicationType,
		ClientName:      doc.ClientName,
		ClientURI:       doc.ClientURI,
		LogoURI:         doc.LogoURI,
		TOSURI:          doc.TOSURI,
		PolicyURI:       doc.PolicyURI,
		RedirectURIs:    doc.RedirectURIs,
		GrantTypes:      doc.GrantTypes,
		ResponseTypes:   doc.ResponseTypes,
	})
	if err != nil {
		return err
	}
	_ = client

	if created && limitErr != nil {
		// Rolls back the INSERT above. Spec § Error Handling makes this a
		// distinct error, NOT the uniform unresolvable one: it "doesn't vary
		// by target host or reveal anything about network reachability", so
		// it falls outside the SSRF-oracle uniform-error rule.
		return ErrClientLimitExceeded
	}

	if created {
		// Fires the alert/hook/event triggers for any quota threshold this
		// creation crossed -- including `action: alert` entries below the
		// blocking quota, which is how an admin hears about approaching
		// exhaustion instead of discovering it from a support ticket.
		// Called AFTER the write is known to have happened, and only for a
		// creation: a refetch crosses no threshold.
		s.UsageLimiter.ReportStandingCreated(ctx, model.UsageNameOAuthClientCIMD, countBefore)
	}

	return nil
}
```

### 3.1 A note on the cache invalidation and the rollback

`Commands.UpsertCIMDClient` schedules its cache invalidation from `DidCommitTx` (Part 3 §2.2). On the `ErrClientLimitExceeded` rollback path, `DidCommitTx` does not run, so no invalidation happens — which is correct: nothing was committed, so nothing is stale. But note that the freshness read earlier in `EnsureClientResolved` will have written a **negative** cache entry for this `client_id` with a 30 s TTL. That is also correct and mildly beneficial: for the next 30 s, a repeat attempt on the same over-quota `client_id` short-circuits at the cache instead of reaching Postgres — though it still performs a fetch, because "not found" and "stale" take the same branch (Part 3 §4.4). Confirm with a test that a second attempt still returns `ErrClientLimitExceeded` and not a stale success.

### 3.2 Error surfacing

Part 3 §6.3 already maps `cimd.ErrClientLimitExceeded` to `access_denied` at `/oauth2/authorize`:

```go
	case errors.Is(err, cimd.ErrClientLimitExceeded):
		return &AuthorizationResultError{
			ResponseMode: r.ResponseMode(),
			Response:     protocol.NewErrorResponse("access_denied", "the project has reached its client limit"),
		}
```

[Part 8](2026-08-31-08-audit-log.md) additionally emits `oauth.client.resolution.failed` with `outcome: "limit_exceeded"` here, so an admin can see that a client was refused rather than only hearing about it from a developer.

No `RedirectURI`, so it renders directly rather than redirecting — there is no resolved client and therefore no validated redirect URI to send it to. The wording matches `POST /oauth2/register`'s equivalent (`handler_register.go`: `access_denied` / "the project has reached its dynamic client registration limit") closely enough to be recognisable while naming the right limit.

## 4. `CountClientsBySource` semantics — confirmed

## 5. The asymmetry, restated for CIMD — worse than DCR's, and accepted

DCR Part 2 §5.1.1 flagged that a standing limit does not self-heal: a rate bucket refills, a periodic usage limit resets, but an exhausted `oauth_client_dcr` quota stays exhausted until a human calls `deleteDynamicClient`. Spec § Client Limit says the CIMD case is sharper, and it is worth spelling out exactly how:

- For DCR, deleting a client is durable — that `dcrc_` id is gone forever and nothing can recreate it.
- For CIMD, `deleteDynamicClient` only evicts the *current* record. The same `client_id` produces a new record on its very next successful resolution at `/oauth2/authorize`. So an admin clearing space against an attacker who is still sending traffic is in a losing race.

What actually contains this:

1. **`allowed_domains`** — the only durable control. A domain removed from the allowlist can never produce a *new* record, because creation requires a fetch and the allowlist is checked on the fetch path (Part 1 §4.1). So removal plus `deleteDynamicClient` *is* a durable ban: the row is gone and cannot be recreated. Removal on its own is not — an existing record keeps resolving, frozen at its last successful fetch. Spec § Domain Trust calls this "the closest thing to one"; the spec update in §8 should say exactly how the two combine.
2. **The Part 4 per-project fetch limit** (10/min) bounds how fast an attacker can create records at all — so quota exhaustion takes minutes, not seconds, and the `action: alert` entry has time to fire.
3. **`enabled: false`** stops it entirely.

**Manual eviction already exists and is the v1 answer.** `deleteDynamicClient` (`pkg/admin/graphql/oauth_client_mutation.go`) takes a `client_id`, is source-agnostic, deletes the `_auth_oauth_client` row, invalidates the resolver cache from `DidCommitTx`, and emits an audit event. Nothing needs building for an admin to reclaim a quota slot. Earlier drafts of this section said "no eviction mechanism is in scope", which read as though nothing existed at all — what is out of scope is only **automatic** eviction.

**Decision: automatic eviction is out of scope, but it is a cheaper follow-up for CIMD than this plan set previously implied.** Three facts, all verified, make it much less invasive than the DCR equivalent:

- **Deleting a dynamic client row destroys no user-facing state.** `DCRFacade.DeleteClient` → `dcr.Commands.DeleteClient` → `oauthclient.Commands.DeleteClient` deletes the row and invalidates the cache, and that is all: it does **not** revoke authorizations or offline grants (DCR Part 2 §6.4 already flagged that as a known gap). So evicting a row does not sign anyone out.
- **A CIMD `client_id` survives eviction, because it is the URL.** The row is a cache of externally-hosted data; the next `/oauth2/authorize` recreates it by fetching, under the same `client_id`, so any existing authorization for that `client_id` still applies. Evicting a DCR client is the opposite — the `dcrc_` id is gone forever and the client must re-register into a new identity.
- **A liveness signal already exists for CIMD and only for CIMD.** `last_fetched_at` is written on every successful fetch, and a fetch happens *only* as a side effect of `/oauth2/authorize` (Part 3 §1.1). So "no successful fetch in N days" is a sound proxy for "no authorization attempt in N days", at the timescale eviction cares about. For DCR the column is always `NULL`, so there is no equivalent signal and eviction would need new bookkeeping.

So the shape of the follow-up is concrete: a background sweep deleting `source = 'CIMD'` rows whose `last_fetched_at` is older than some threshold, reusing `Commands.DeleteClient` so cache invalidation and audit logging come for free. That restores the self-healing property the standing quota otherwise lacks.

Two reasons it still should not be in this plan set:

- **It needs a policy decision cimd.md does not make.** What threshold? Does eviction emit the same audit event as an admin delete, or a distinct one? Does it respect a project that has deliberately parked a client?
- **There is one real behavior change to accept first.** A client whose document has gone permanently offline currently keeps working forever on its stale record (Part 3 §5), and its `last_fetched_at` stops advancing — so it looks dead to exactly this sweep and would be evicted, after which its next authorization fails outright. That is arguably the correct outcome for a client running on frozen metadata, but it converts "works indefinitely" into "breaks after N days", and that is a product call, not an implementation detail.

Do not read this as a commitment. It is written out so that whoever picks it up does not start from scratch, and so a reviewer asking "why not just evict?" gets the actual answer.

Recommend in the PR description that any plan tier setting an `oauth_client_cimd` block also set a lower `action: alert` entry alongside the `action: block` one, for the same reason DCR Part 2 recommends it.

## 7. Fixed Behavioral Decisions

- **D1. The limit is checked speculatively and re-decided against the upsert's `created` flag, with a rollback.** Only this ordering satisfies both spec requirements at once — a new `client_id` at quota is refused, an existing one is never affected regardless of the count — without a second existence query that would itself be a TOCTOU hazard.
- **D2. A refetch of an existing `client_id` is never blocked, even when the project is over quota.** Spec § Client Limit, verbatim. Including after a plan downgrade left the project above its new quota.
- **D3. `ErrClientLimitExceeded` → `access_denied`, distinct from the uniform unresolvable error.** Spec § Error Handling's explicit carve-out from the SSRF-oracle rule.
- **D4. `ReportStandingCreated` fires only on a creation**, after the write, so `action: alert` thresholds are crossed once per real new client and a refetch is silent.
- **D5. A per-app, per-source advisory lock wraps count-then-upsert.** The Part 3 single-flight guard is per-`client_id` and does not cover the two-different-new-clients race for the last slot.
- **D6. No `oauth_client_cimd` key is added to `authgear.yaml`'s `usage.limits`.** Plan-tier only.
- **D7. `oauth_client_cimd` and `oauth_client_dcr` are independent quotas.** Already guaranteed by `CountClientsBySource`; asserted by test.
- **D8. No *automatic* eviction.** §5. Manual eviction already exists (`deleteDynamicClient`) and is the v1 answer; the non-self-healing quota is accepted, with `allowed_domains` + `deleteDynamicClient` as the durable containment and the Part 4 fetch limit as the rate containment. §5 records the concrete shape of an automatic sweep and the one behavior change it would introduce, for whoever picks it up.

## 8. Spec Updates

`doc:` commit against `docs/specs/cimd.md`:

1. **§ Client Limit**: state explicitly that a refetch of an existing `client_id` succeeds even when the project is *over* quota (not merely at it) — e.g. after a plan downgrade. The current text ("A `client_id` that already has a persisted record is unaffected regardless of the limit") implies this; make it unambiguous.
2. **§ Domain Trust**: spell out that `allowed_domains` plus `deleteDynamicClient` together *do* form a durable ban, while allowlist removal alone stops only new clients and refetches — an existing client keeps working on frozen metadata. § Client Limit currently says the delete alone is not a ban and points here, so this is where the combination has to be stated. (Part 1 §9 item 3 makes the same edit; whichever lands first should carry it.)
3. **§ Client Limit**: note that the [per-project fetch rate limit](2026-08-28-04-rate-limits.md) bounds how fast the quota can be consumed, so an `action: alert` entry has time to fire.

Also add `oauth_client_cimd` to [docs/specs/usage.md § Supported usage names](../../specs/usage.md#supported-usage-names) as a standing name alongside `oauth_client_dcr` — check how that table describes `oauth_client_dcr` and mirror it.
