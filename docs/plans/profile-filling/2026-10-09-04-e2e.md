# Profile Filling — Part 4: E2E tests

Spec: [profile-filling.md § Use cases](../../specs/user-profile/profile-filling.md#use-cases).

Parts: [1 Attribute validation](./2026-10-09-01-attribute-validation.md) · [2 Authflow](./2026-10-09-02-authflow.md) · [3 Auth UI](./2026-10-09-03-auth-ui.md) · **4 E2E**

## 1. Scope

YAML e2e tests for the Authflow API behavior from Parts 1 and 2. The tests check state after each flow with `query` on `_auth_user` and `audit_query` on `_audit_log`, as the `write-e2e-test` skill requires. Auth UI is covered by unit tests and manual checks (Part 3).

## 2. Layout

```
e2e/tests/profile_filling/
  var/deno/
    form_reject_all.ts         # always is_allowed: false
    form_check_employee.ts     # see below
    form_reject_unknown.ts     # invalid_form_field on /x_not_in_form
    form_bad_reason_type.ts    # reasons[0].type = "unknown"
    profile_pre_update_reject.ts
  *.test.yaml
e2e/tests/hook/authentication.form.post_submitted/
  var/deno/                    # its own copies of the scripts it uses
  *.test.yaml
```

Each test sets `extra_files_directory: ./var` and the required `authentication_flow` plus `user_profile` in `authgear.yaml.override`.

How the tests check things:

- **Blocking events are not in `_audit_log`.** The audit sink ignores them (`pkg/lib/audit/sink.go:22`). So assertions about `authentication.form.post_submitted` are made by the Deno scripts, which reject when the payload is not what they expect. `form_check_employee.ts` returns `is_allowed: true` only when `e.payload.form.name === "employee"` and `e.payload.user.custom_attributes.x_employee_id` equals the submitted value. For `E99999` it returns `invalid_form_field` on `/x_employee_id`. The e2e hook server cannot be used, because it answers `{"result":"ok"}`, which is not a valid blocking response (`e2e/cmd/hookserver/main.go:235`).
- **Non-blocking events are asserted with `audit_query`.** These are `user.created`, `user.profile.updated`, `user.authenticated`, and `user.anonymous.promoted`. When order matters, use `ORDER BY (data->>'seq')::bigint`, because `created_at` has one-second precision (`audit/log.go:44`).
- **Fixture users with values that break a constraint are inserted with `custom_sql`.** Part 1 checks constraints on user import too.
- **Config rejection cannot be tested in e2e.** `create-configsource` runs `config.Parse`, so an invalid config fails test setup (`e2e/cmd/e2e/pkg/configsource.go:112`). Those cases live in Part 2's Go config testdata.

## 3. Cases

| File | Flow | Asserts |
|---|---|---|
| `profile_filling/signup_fill_form.test.yaml` (UC1) | email → verify → password → `fill_form` | `action.type: fill_form` with `data.type: fill_form_data` and fields `/given_name`, `/family_name` (`type: string`, `required: true`, label "Given name"); input without `/family_name` → `ValidationFailed`, then the same `state_token` with both → `finished`; `_auth_user.standard_attributes->>'given_name' = 'John'`; `audit_query` on `user.created` has `data->'payload'->'user'->'standard_attributes'->>'given_name' = 'John'`. |
| `profile_filling/signup_identify_form.test.yaml` (UC2) | username with branch `form`, hook `form_reject_all.ts` | `identify` option has `form.fields`; `fields` sent on another branch without a form → `ValidationFailed`; input missing required `/given_name` → `ValidationFailed`, flow stays in `identify`; taken username (fixture user via `user_import`) → the duplicate login ID error, not `HookDisallowed`, which proves the form hook was not called. Valid input is covered by `signup_identify_form_success.test.yaml` below. |
| `profile_filling/signup_identify_form_success.test.yaml` (UC2) | username with branch `form`, no hook | valid input → `create_authenticator`; after finish, `given_name` stored and `family_name` absent. |
| `profile_filling/multi_page.test.yaml` (UC3) | two `fill_form` steps, both all-optional | page 1 submitted as `{"fields": []}` → the response is the page-2 `fill_form` action (not `finished`), which proves one input is not consumed by two forms; page 2 `{"fields": []}` → `finished`; optional enum stored only when sent. |
| `profile_filling/constraints.test.yaml` (UC4, UC7) | custom `pattern`, standard `validation` `min_length`/`allowed_characters` | `12345` → `ValidationFailed` with cause `kind: pattern` at `/fields/0/value`; `Ace!` → `kind: allowedCharacters`; `Ac` → `kind: minLength`; valid values finish. `fill_form_data.fields[0].constraints` includes `pattern` and `pattern_message`. |
| `profile_filling/boolean_terms.test.yaml` (UC8) | boolean custom attributes | label contains the `<a href>` link; required boolean with `false` → `ValidationFailed`; `true` + optional `false` → stored as JSON `true`/`false`; `user.created` payload has both. |
| `profile_filling/address.test.yaml` (UC5) | flow group `store` with required `/address` | `create` with `{"type": "signup", "name": "store"}`; `fields[0].type: address`; `{}` → `ValidationFailed`; `{"foo": "x"}` → `ValidationFailed`; an address with `street_address`, `locality`, `country` → stored as one object. |
| `profile_filling/current_values.test.yaml` (UC6 without population) | two `fill_form` steps sharing `/given_name` | The mock OIDC provider used by `account_linking/incoming_oauth_*` returns no name claims (`e2e/cmd/proxy/mockoidc/user.go:35-58`), so population cannot be exercised without changing the mock. Instead, a first `fill_form` sets the value. The second form's `fields[0].value` equals the first submission, and an omitted optional field is cleared in `_auth_user`. |
| `profile_filling/login_fill_form.test.yaml` | login: identify → `fill_form` → authenticate | Form shown before password; after finish, attribute stored; `audit_query` ordered by `seq` shows `user.profile.updated` before `user.authenticated`. Second login: form shown again with the stored `value`. |
| `profile_filling/login_no_form_no_event.test.yaml` | login with no `fill_form` | No `user.profile.updated` in `_audit_log`. |
| `profile_filling/select_account_fill_form.test.yaml` | login with `select_account` branch, then `fill_form` | Existing session set up with the `create_session` step and `session_cookie`, as in `select_account/login_session_reused.test.yaml`; after selecting the account, `action.type: fill_form`; submit → `finished`; attribute stored. |
| `profile_filling/promote_fill_form.test.yaml` (UC7) | promote with `fill_form` | Based on `tests/promote/` (anonymous `login_hint` and the `create_challenge` step); `type: promote` with `fill_form`; after finish, same user ID, `nickname` stored; `audit_query` ordered by `seq` shows `user.anonymous.promoted` then `user.profile.updated`. |
| `profile_filling/signup_login_identify_form.test.yaml` | signup_login → signup whose email branch has `form` | After the login ID, `action.type: fill_form` (not `identify`) with the branch's fields; submit → finish; attribute stored. |
| `profile_filling/account_linking_skips_form.test.yaml` | signup: email identify → `fill_form` → OAuth identify that links into an existing user | Based on `account_linking/incoming_oauth_*`. The form is submitted before linking; the flow then continues as the existing user and finishes (no broken replay); the existing user's attribute is unchanged; no `user.created`. |
| `profile_filling/form_order_before_otp.test.yaml` (UC9) | phone identify → `fill_form` → SMS OTP, `phone_otp_mode: sms` (as `tests/events/sms.suppressed`) | Rejected form (`form_check_employee.ts`, `E99999`) keeps `fill_form`; `sms.suppressed` count 0; accepted form → `sms.suppressed` count 1. |
| `hook/authentication.form.post_submitted/reject_field.test.yaml` (UC4) | signup `fill_form` with `form.name: employee`, `form_check_employee.ts` | `E99999` → error `Forbidden`/`HookDisallowed`, `info.reasons[0].reasons[0] == {type: invalid_form_field, key: "/x_employee_id", message: "…"}`; same `state_token` with `E10234` → next step. The script allowing `E10234` proves `form.name` and the user's applied attribute were in the payload. |
| `hook/authentication.form.post_submitted/unknown_key_kept.test.yaml` | hook returns a key not in the form | `HookDisallowed` with that key in `reasons`. |
| `hook/authentication.form.post_submitted/invalid_reason_type.test.yaml` | hook returns unknown reason type | error `HookInvalidResponse`. |
| `hook/authentication.form.post_submitted/login.test.yaml` | login `fill_form` with blocking `user.profile.pre_update` reject script | form accepted; the final input fails with `HookDisallowed` from `user.profile.pre_update`; attribute not stored. |
| `admin_api/custom_attribute_constraints.test.yaml` | Admin API `updateUser` | Fixture user inserted with `custom_sql`, already holding a value that breaks the new `pattern`. Changing `/x_employee_id` to `12345` → `ValidationFailed` (`kind: pattern`); updating another attribute while the old invalid value stays → succeeds, showing constraints apply only to changed values. |

## 4. Running

```bash
cd e2e
make teardown && make setup
go test ./pkg/testrunner/ -count 1 -v -timeout 10m -run "TestAuthflow/profile_filling"
go test ./pkg/testrunner/ -count 1 -v -timeout 10m -run "TestAuthflow/hook/authentication.form.post_submitted"
go test ./pkg/testrunner/ -count 1 -v -timeout 10m -run "TestAuthflow/admin_api/custom_attribute_constraints"
```
