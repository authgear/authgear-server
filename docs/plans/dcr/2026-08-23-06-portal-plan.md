# DCR Part 6 — Portal Configuration (Implementation Plan)

Design: [2026-08-23-06-portal-design.md](./2026-08-23-06-portal-design.md).
Spec: [docs/specs/dcr.md](../../specs/dcr.md). Ticket: DEV-3801.

## 1. Goal / Scope

Frontend-only. Build the portal UI for DCR on top of the Admin API and config
surface that PR #5870 (parts 1–5) already ships. **No Go changes, no GraphQL
schema changes, no migrations.** Everything below consumes:

- Admin API (already in `portal/src/graphql/adminapi/schema.graphql` on the
  #5870 branch): `dynamicClients` connection, `deleteDynamicClient`,
  `initialAccessTokens`, `createInitialAccessToken`,
  `revokeInitialAccessToken`, `Resource.accessPolicy`, `Scope.accessPolicy`,
  `AccessPolicyInput` on `CreateResourceInput` / `UpdateResourceInput` /
  `CreateScopeInput` / `UpdateScopeInput`.
- App config: `oauth.dynamic_client_registration`
  (`pkg/lib/config/oauth_dynamic_client_registration.go`), saved through the
  existing portal `updateApp` config mutation — no new portal-backend code.
- Feature config: `usage.limits.oauth_client_dcr`
  (`pkg/lib/config/feature_usage.go`), readable from the existing
  `effectiveFeatureConfig` JSON blob (`appFeatureConfigQuery`).

Base branch: `main` after #5870 merges (or stacked on `dev-3792-dcr` before
that). Coordination note: if the Radix migration PR #5861 merges first,
`ApplicationsConfigurationScreen.tsx` will have been rewritten — the tab
insertion in §5.1 applies to whichever version is current; all NEW components
in this plan use `portal/src/components/v2/*` (Radix) regardless.

Out of scope: rate-limit UI, per-client overrides, RFC 7592, CIMD-specific UI,
registering clients from the portal (see design §3).

### 3.2 Config form

Use `useAppConfigForm` (`portal/src/hook/useAppConfigForm.ts`) exactly like
other configuration screens:

- `constructFormState(config)` →
  `{ enabled, initialAccessTokenRequired, accessTokenLifetimeSeconds, refreshTokenLifetimeSeconds, refreshTokenIdleTimeoutEnabled, refreshTokenIdleTimeoutSeconds }`
  where `initialAccessTokenRequired` defaults to `true` when
  `initial_access_token_required` is absent (matches
  `IsInitialAccessTokenRequired()` semantics) and lifetime fields are
  `number | undefined` (undefined = unset, show effective default as
  placeholder: 1800 / 2592000 / true / 1209600 — the constants in
  `OAuthDynamicClientRegistrationDefaultClientConfig.SetDefaults`).
- `constructConfig(config, initialState, currentState)` → `produce` +
  `clearEmptyObject`, writing `oauth.dynamic_client_registration`. Write
  `initial_access_token_required: false` explicitly when off; when on, omit
  the field (spec default). Omit unset lifetime fields.

Rendering: `ScreenContent` + `ScreenTitle` + `FormContainer` (save bar), three
`Widget`/`SettingsSectionCard` sections per design §5.2, using
`components/v2` `Toggle` and `TextField`.

Turn-off-IAT confirmation: local state + `components/v2/ConfirmationDialog`.
Flow: toggle change to `false` → open dialog → confirm sets form state /
cancel reverts. Toggling on never prompts.

### 3.3 IAT management section

Inside the Registration security section, below the toggle. Data via
`useInitialAccessTokensQueryQuery` (generated hook); actions:

- `InitialAccessTokenList`: rows of type badge (`components/v2/Badge`;
  FIRST_PARTY uses warning styling), createdAt, expiresAt (formatted with the
  existing date util used by the screen's neighbors), Revoke button per row.
  Revoke → `ConfirmationDialog` → `revokeInitialAccessToken` → refetch
  `initialAccessTokensQuery`.
- `CreateInitialAccessTokenDialog`: type radio (default `THIRD_PARTY`;
  choosing `FIRST_PARTY` reveals inline warning text), expiry select mapping
  to `expiresIn` seconds: 3600 / 86400 / 604800 / 2592000. Submit →
  `createInitialAccessToken` → close → open `InitialAccessTokenRevealDialog`
  with the returned `token` → refetch list.
- `InitialAccessTokenRevealDialog`: read-only copy field (`useCopyFeedback` +
  `components/v2/CopyIconButton`, same pattern as the IdP certificate
  fingerprint copy field, commit 2ee39cc15b) + "shown once" notice. Closing
  discards the plaintext; no way to re-open.

IAT actions run immediately and do not touch the config form's dirty state.

- Pagination: follow `APIResourcesScreen.tsx:25-47` — `PAGE_SIZE = 10`,
  offset state, `encodeOffsetToCursor(offset)` as `after`, `PaginationWidget`.
  The `dynamicClients` resolver uses the same shared relay helper, so
  offset-encoded cursors work identically.
- Props needed from the screen: `effectiveAppConfig` (already loaded there)
  for `oauth.dynamic_client_registration.enabled` and
  `http.public_origin`; `effectiveFeatureConfig` via the screen's existing
  `useAppFeatureConfigQuery` for the cap.
- Header: registration endpoint copy field
  (`${effectiveAppConfig.http?.public_origin}/oauth2/register`); cap line
  "N of Q" where `Q = min(quota of entries with action "block")` from
  `effectiveFeatureConfig.usage?.limits?.oauth_client_dcr`, hidden when no
  such entry; `N = totalCount`. "Registration settings" button → `./dcr`
  relative navigate.
- Row click → `DynamicClientDetailsDialog` (read-only fields per design
  §5.1; clientID via copy field). Delete button in dialog footer and as row
  action → `DeleteDynamicClientDialog` (warning: already-issued tokens stay
  valid until expiry) → `deleteDynamicClient(clientID)` → refetch
  `dynamicClientsQuery` (reset offset to 0 if the current page becomes empty).
- Disabled empty state: shown when
  `!effectiveAppConfig.oauth?.dynamic_client_registration?.enabled`, without
  issuing the `dynamicClients` query (`skip: true`).

implemented as a new component

- Toggle bound to `resource.accessPolicy.allowDynamicThirdPartyClientAccess`.
- On change → `useUpdateResourceMutationMutation` with

## 7. Compatibility / Rollout

- Config written by the settings screen validates against
  `OAuthDynamicClientRegistrationConfig`'s JSON schema; `rate_limits` set via
  the raw editor survives round-trips untouched (form only writes the keys it
  owns via immer produce on the full config document).
- `effectiveFeatureConfig.usage` absent (older plans / no limit) → cap line
  hidden; nothing breaks.
- Portal deployed against a server without #5870 is not supported (the
  adminapi schema would reject the new operations); this feature ships after
  #5870 merges. No dual-read/dual-write concerns — no persisted state is
  introduced by this part.

## 8. Test Plan

- `cd portal && npm run typecheck` and `make -C portal lint` after every
  commit; `npm run gentype` must be diff-clean at HEAD.
- No new unit tests: the portal codebase does not unit-test screens, and all
  new logic is thin view code over generated hooks. `constructConfig` /
  `constructFormState` for the settings screen are pure and small; if a
  regression appears there, cover with a vitest-style test then — not
  speculatively now.
- No new Storybook stories (matches `components/api-resources`, which has
  none).
- Manual verification (per project owner's workflow: visual testing is done
  by the reviewer, not automated browser runs): walk design §6 UF1–UF4
  against a local server running #5870 with the PR description's test setup.

## 9. Fixed Behavioral Decisions

- IAT expiry choices: 1h / 24h / 7d / 30d; `expiresIn` always sent explicitly.
- IAT list shows active tokens only (that is all the API returns).
- IAT section visible under open registration (first-party IATs still work).
- Cap "Q" = smallest `quota` among `action: "block"` entries; `alert` entries
  never rendered.
- Dynamic client list order = server order (registeredAt desc from the relay
  store); no client-side sorting.
- `source` (DCR/CIMD) shown only in the details dialog.
- Delete resets pagination to page 1 only when the current page empties.
- Toggling resource-level dynamic access off requires confirmation; scope
  checkbox does not (saved via the form's explicit Save).
