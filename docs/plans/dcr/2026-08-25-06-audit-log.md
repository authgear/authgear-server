# DCR Part 6 — Audit Log Events

Spec: [docs/specs/event.md — oauth.client.registered](../../specs/event.md#oauthclientregistered), [docs/specs/dcr.md — Audit Log](../../specs/dcr.md#audit-log), [docs/specs/audit-log.md](../../specs/audit-log.md).

Depends on Part 1 (IAT management — `pkg/lib/dcr`, `createInitialAccessToken`/`revokeInitialAccessToken`) and Part 2 (`POST /oauth2/register`, `deleteDynamicClient`). Everything those parts introduced is already merged; this part only adds event emission on top of the existing call paths.

## 1. Goal / Scope

Make every DCR lifecycle action visible in the audit log. Four new non-blocking event types, none of them delivered to webhooks:

| Event type | Emitted from | GraphQL enum value |
|---|---|---|
| `oauth.client.registered` | `POST /oauth2/register`, after the client row is created | `OAUTH_CLIENT_REGISTERED` |
| `admin_api.mutation.create_initial_access_token.executed` | `createInitialAccessToken` mutation | `ADMIN_API_MUTATION_CREATE_INITIAL_ACCESS_TOKEN_EXECUTED` |
| `admin_api.mutation.revoke_initial_access_token.executed` | `revokeInitialAccessToken` mutation | `ADMIN_API_MUTATION_REVOKE_INITIAL_ACCESS_TOKEN_EXECUTED` |
| `admin_api.mutation.delete_dynamic_client.executed` | `deleteDynamicClient` mutation | `ADMIN_API_MUTATION_DELETE_DYNAMIC_CLIENT_EXECUTED` |

All four are `ForAudit() == true`, `ForHook() == false` — the same shape as the 56 existing `admin_api.mutation.*.executed` payloads (verified: every one of them returns `false` from `ForHook`) and `m2m.token.created`. They are recorded in `_audit_log` and surfaced through the Admin API `auditLogs` query and the portal Audit Log screen; they are **not** delivered to webhooks or the Event API.

**Out of scope:**

- Failed registration attempts. A rejected `POST /oauth2/register` (bad metadata, invalid IAT, quota reached) produces no audit row. Rate-limited attempts are already covered by the existing `rate_limit.blocked` event, which `pkg/lib/ratelimit` emits for every bucket including `oauth.register.per_ip` / `oauth.register.per_project`. Adding a failure event would mean an unauthenticated caller can write unbounded audit rows under open registration; that is a separate design question, not a gap this part leaves open by accident.
- Webhook/Event API delivery for these types (`ForHook: false`, per the table above).
- CIMD (`source: CIMD`). `oauth.client.registered` carries a `source` field so a CIMD resolution can reuse the same event type later, but no CIMD emitter exists in this codebase.
- Any RFC 7592 client self-service events — those endpoints do not exist yet.

## 2. Event Payloads

New files under `pkg/api/event/nonblocking/`, one payload per file, matching the existing one-type-per-file convention that `TestPayloadRegistryIsComplete` (`pkg/api/event/resolve_tag_invariant_test.go`) enforces by counting source files.

Every payload is a **purpose-built struct with explicit `json` tags**, not an embedded `model.OAuthClient` / `model.OAuthInitialAccessToken`. Two reasons, both concrete:

1. Neither model carries `json` tags today (`pkg/api/model/oauth_client.go`, `pkg/api/model/oauth_initial_access_token.go` — the GraphQL layer resolves them field-by-field and never marshals them). Embedding either one would write PascalCase keys (`"ClientID"`, `"ExpiresAt"`) into `_audit_log.data.payload`, inconsistent with every other payload in the package.
2. `model.OAuthClient` has 30 fields, most of them resolved token-lifetime settings that are irrelevant to an audit record. A purpose-built struct keeps the audit row to what an auditor actually needs.

`oauth.client.registered` groups its fields under `client` and `initial_access_token` sub-objects because it is the one payload here that is **documented in `docs/specs/event.md`**, and every documented payload in that file nests under a domain object (`"user"`, `"usage"`, `"rate_limit"`). The three Admin API payloads are not documented in any spec — matching the 56 existing `admin_api.mutation.*` payloads, none of which appears in event.md — so they stay flat, matching those.

### 2.1 `oauth_client_registered.go`

```go
package nonblocking

import (
	"github.com/authgear/authgear-server/pkg/api/event"
	"github.com/authgear/authgear-server/pkg/api/model"
)

const (
	OAuthClientRegistered event.Type = "oauth.client.registered"
)

type OAuthClientRegisteredEventPayloadClient struct {
	ClientID        string                  `json:"client_id"`
	Source          model.OAuthClientSource `json:"source"`
	Kind            model.OAuthClientKind   `json:"kind"`
	ClientName      string                  `json:"client_name,omitempty"`
	ApplicationType string                  `json:"application_type,omitempty"`
	RedirectURIs    []string                `json:"redirect_uris"`
	GrantTypes      []string                `json:"grant_types"`
	ResponseTypes   []string                `json:"response_types"`
}

type OAuthClientRegisteredEventPayloadInitialAccessToken struct {
	ID   string                            `json:"id"`
	Type model.OAuthInitialAccessTokenType `json:"type"`
}

type OAuthClientRegisteredEventPayload struct {
	Client OAuthClientRegisteredEventPayloadClient `json:"client"`

	// InitialAccessToken is nil under open registration
	// (initial_access_token_required: false), and the `omitempty` drops the
	// key entirely — which is exactly the signal an auditor wants. An absent
	// key means "anyone who could reach the endpoint could have done this";
	// a present one names the IAT that authorized it, so a leaked IAT can be
	// traced to every client it registered. A pointer, not a value struct,
	// because "no IAT" must be distinguishable from "an IAT with empty
	// fields". docs/specs/event.md documents the key as absent, not null.
	InitialAccessToken *OAuthClientRegisteredEventPayloadInitialAccessToken `json:"initial_access_token,omitempty"`
}

func (e *OAuthClientRegisteredEventPayload) NonBlockingEventType() event.Type {
	return OAuthClientRegistered
}

func (e *OAuthClientRegisteredEventPayload) UserID() string { return "" }

func (e *OAuthClientRegisteredEventPayload) GetTriggeredBy() event.TriggeredByType {
	return event.TriggeredByTypeUser
}

// FillContext sets ClientID so the _audit_log.client_id column names the
// client that was just created, matching M2MTokenCreatedEventPayload
// (m2m_token_created.go:28-30), the only other event emitted from an OAuth
// endpoint with no authenticated user. docs/specs/event.md documents this as
// part of the event's contract ("context.client_id is the client_id of the
// newly registered client").
func (e *OAuthClientRegisteredEventPayload) FillContext(ctx *event.Context) {
	ctx.ClientID = e.Client.ClientID
}

func (e *OAuthClientRegisteredEventPayload) ForHook() bool  { return false }
func (e *OAuthClientRegisteredEventPayload) ForAudit() bool { return true }

func (e *OAuthClientRegisteredEventPayload) RequireReindexUserIDs() []string { return nil }
func (e *OAuthClientRegisteredEventPayload) DeletedUserIDs() []string        { return nil }

var _ event.NonBlockingPayload = &OAuthClientRegisteredEventPayload{}
```

`GetTriggeredBy` returns `TriggeredByTypeUser`, not `TriggeredBySystem`. `event.TriggeredByType` has no branching consumer anywhere in the server — `grep -rn "TriggeredBy\b"` over `pkg/` outside `GetTriggeredBy`/`TriggeredByType` declarations hits exactly two assignment sites (`pkg/lib/event/service.go:272`, `pkg/portal/service/audit.go:141`), both of which just copy the value into the event context. So the choice is purely descriptive, and `user` is the value `m2m.token.created` already uses for the same situation: a request that arrived at a public OAuth endpoint from outside, not from the Admin API and not from a background job.

### 2.4 `adminapi_mutation_deletedynamicclient_executed.go`

```go
const (
	AdminAPIMutationDeleteDynamicClientExecuted event.Type = "admin_api.mutation.delete_dynamic_client.executed"
)

type AdminAPIMutationDeleteDynamicClientExecutedEventPayload struct {
	ClientID   string                  `json:"client_id"`
	Source     model.OAuthClientSource `json:"source"`
	Kind       model.OAuthClientKind   `json:"kind"`
	ClientName string                  `json:"client_name,omitempty"`
}

// FillContext sets ClientID for the same reason as
// OAuthClientRegisteredEventPayload: it makes "everything that ever happened
// to client X" a single indexed query on _audit_log.client_id rather than a
// jsonb scan over data->'payload'. This is a deliberate deviation from the
// other 56 admin_api.mutation.* payloads, whose FillContext is empty — none
// of them is about an OAuth client, so none of them has a client id to put
// there.
func (e *AdminAPIMutationDeleteDynamicClientExecutedEventPayload) FillContext(ctx *event.Context) {
	ctx.ClientID = e.ClientID
}
```

Remaining methods as in §2.2 (`GetTriggeredBy` → `TriggeredByTypeAdminAPI`).

`Source` and `Kind` are recorded because deletion is destructive and the row is gone afterwards — the audit log is the only remaining record of what was deleted. `Source` in particular is what distinguishes "an admin deleted a DCR client, permanently freeing a quota slot" from "an admin evicted a CIMD record that can reappear on the next resolution" (docs/specs/dcr.md — New mutation).

## 4. Runtime — Emission

### 4.1 `POST /oauth2/register`

Entry point: `RegistrationHandler.Handle` (`pkg/lib/oauth/handler/handler_register.go:105`).

Add one field to the struct. **Reuse the package's existing `EventService` interface** (`handler_token.go:78-81`) rather than declaring a `RegistrationHandlerEventService` — it is already `DispatchEventOnCommit` + `WillDeliverBlockingEvent`, already bound to `*event.Service` by wire for `TokenHandler` in the same package:

```go
type RegistrationHandler struct {
	Database    *appdb.Handle
	OAuthConfig *config.OAuthConfig
	DCR         RegistrationHandlerDCRService
	IAT         RegistrationHandlerIATService
	Clock       clock.Clock
	Events      EventService // new

	RemoteIP     httputil.RemoteIP
	RateLimiter  RegistrationHandlerRateLimiter
	UsageLimiter RegistrationHandlerUsageLimiter
}
```

Inside the existing `h.Database.WithTx` closure (`handler_register.go:160-201`), two changes:

1. Hoist the IAT out of the `if token != ""` block so its id and type survive to the dispatch. Today `iat` is a block-local whose only use is `iat.Type` (`handler_register.go:163-169`):

```go
var iat *model.OAuthInitialAccessToken   // declared alongside `client` and
                                         // `countBeforeCreate`, outside WithTx
...
kind := model.OAuthClientKindThirdParty
if token != "" {
	t, err := h.IAT.ValidateAndGetByToken(ctx, token)
	if err != nil {
		return err
	}
	iat = t
	if iat.Type == model.OAuthInitialAccessTokenTypeFirstParty {
		kind = model.OAuthClientKindFirstParty
	}
}
```

2. Dispatch immediately after `h.DCR.RegisterClient` succeeds, still inside the transaction — `DispatchEventOnCommit` calls `s.Database.UseHook(ctx, s)`, which requires an active transaction, and the audit row must not be written if the client insert rolls back:

```go
	c, err := h.DCR.RegisterClient(ctx, &dcr.RegisterClientOptions{...})
	if err != nil {
		return err
	}
	client = c

	payload := &nonblocking.OAuthClientRegisteredEventPayload{
		Client: nonblocking.OAuthClientRegisteredEventPayloadClient{
			ClientID:        client.ClientID,
			Source:          client.Source,
			Kind:            client.Kind,
			ClientName:      client.Name,
			ApplicationType: derefStringOr(client.ApplicationType, ""),
			RedirectURIs:    client.RedirectURIs,
			GrantTypes:      client.GrantTypes,
			ResponseTypes:   client.ResponseTypes,
		},
	}
	if iat != nil {
		payload.InitialAccessToken = &nonblocking.OAuthClientRegisteredEventPayloadInitialAccessToken{
			ID:   iat.ID,
			Type: iat.Type,
		}
	}
	if err := h.Events.DispatchEventOnCommit(ctx, payload); err != nil {
		return err
	}
	return nil
```

`derefStringOr` already exists in this file (`handler_register.go:238`) and is used by the response builder; no new helper.

Full call sequence, unchanged except for the two additions:

1. `Handle` → DCR-enabled check → `h.checkRateLimit` ×2 → `Authorization` header parse → `json.Decode` → `dcr.ValidateAndNormalize`.
2. `h.Database.WithTx`:
   1. `h.IAT.ValidateAndGetByToken` (only when a token was presented) → **`iat` retained**, `kind` derived.
   2. `h.DCR.LockForClientCount` → `h.DCR.CountClientsBySource` → `h.UsageLimiter.CheckStanding`.
   3. `h.DCR.RegisterClient` → `client`.
   4. **`h.Events.DispatchEventOnCommit(&nonblocking.OAuthClientRegisteredEventPayload{...})`** → appends to `event.Service.NonBlockingPayloads` and registers the service as a tx hook. Returns an error only if the hook registration itself fails, which aborts the transaction and the registration — correct, since a registration Authgear cannot record is a registration it should not perform.
3. On commit: `event.Service.WillCommitTx` resolves the payload into an `*event.Event` (assigning the sequence number via `Store.NextSequenceNumber`, still inside the tx); `DidCommitTx` fans out to the sinks, where `audit.Sink.ReceiveNonBlockingEvent` sees `ForAudit() == true` and writes the row through its own `auditdb.WriteHandle` transaction.
4. `h.UsageLimiter.ReportStandingCreated` and the HTTP response, both unchanged.

Failure isolation is inherited, not added: a sink error in `DidCommitTx` is logged and swallowed (`pkg/lib/event/service.go:194-199`), so an audit-database outage cannot fail a registration that has already committed.

**Wiring:** `pkg/auth/wire_gen.go:4618-4627` constructs `RegistrationHandler`. The `EventService` → `*event.Service` binding already exists in the auth request scope (the token handler in the same package uses it), so this is a `make generate` regeneration, not a new provider. The regenerated `wire_gen.go` must land in the same commit.

### 4.3 `deleteDynamicClient`

Entry point: `pkg/admin/graphql/oauth_client_mutation.go:36-48`. Same read-before-delete rationale as §4.2 — the client row is gone after the mutation, so `Source`/`Kind`/`ClientName` must be captured before the delete.

`pkg/lib/oauthclient/commands.go` — `DeleteClient` returns the deleted client:

```go
func (c *Commands) DeleteClient(ctx context.Context, clientID string) (*Client, error) {
	client, err := c.Store.GetClientByClientID(ctx, clientID)
	if err != nil {
		return nil, err
	}
	if err := c.Store.DeleteClientByClientID(ctx, clientID); err != nil {
		return nil, err
	}

	if !c.hooked {
		c.Database.UseHook(ctx, c)
		c.hooked = true
	}
	c.pendingInvalidations = append(c.pendingInvalidations, clientID)
	return client, nil
}
```

The existing doc comment on `DeleteClient` (about deferring cache invalidation to `DidCommitTx`) stays as-is — that behavior is untouched. `Store.GetClientByClientID` already exists (`store_client.go:114`) and hits the same `_auth_oauth_client` table inside the same transaction, so it observes uncommitted state correctly.

## 5. Storage, Compatibility and Deployment

- **No schema change.** `_audit_log` (`docs/specs/audit-log.md`) already stores `activity_type text` and `data jsonb`; the four new types are new values in an existing column, not a new shape.
- **No migration and no backfill.** Audit logs are append-only records of things that happened; actions taken before this ships have no rows and must not gain any.
- **Mixed-version deploy is safe in both directions.** An old `authgear` binary writing rows and a new Admin API reading them is the normal case (the new enum values simply never appear). The reverse — a new binary writing `oauth.client.registered` rows while an old Admin API is still serving `auditLogs` — is also safe: `pkg/admin/graphql/query.go:298` defaults the query to `knownAuditLogActivityTypes`, an allow-list derived from the old binary's enum, so unknown types are filtered out by the `WHERE activity_type = ANY(...)` clause and never reach the enum serializer that would panic on them (the failure mode documented in `docs/plans/siteadmin-api/08-audit-log.md`). Rows written during the window become visible as soon as the Admin API is upgraded.
- **Credential handling.** No plaintext IAT and no client secret enters `_audit_log`. This is a hard requirement of §2.2, not a preference: `_audit_log` has 90-day retention and is readable by every project admin through the portal.
- **`.vettedpositions`.** None of the touched packages (`pkg/api/event/...`, `pkg/admin/graphql`, `pkg/lib/dcr`, `pkg/lib/oauthclient`, `pkg/lib/oauth/handler`) has an entry in the file. Run `make update-vettedpositions` only if goanalysis reports drift.

## 7. Spec Updates

Landed as the first commit, ahead of the implementation.

Only `oauth.client.registered` is specified. The three `admin_api.mutation.*.executed` types are deliberately left out of the specs, because none of the 56 existing ones is specified either — they are an implementation-level convention of the Admin API, not part of its documented contract, and documenting three of fifty-nine would be worse than documenting none.

- **`docs/specs/event.md`** — `oauth.client.registered` documented as an ordinary non-blocking event: added to the Non-blocking Events index, given a `#### oauth.client.registered` section with an example payload and a field-by-field description, and added to the `### Events that support audit log` list. `rate_limit.blocked` is the precedent for documenting a `ForHook: false` event this way — it is in both lists already and carries no special caveat, so `oauth.client.registered` does not need one either.
- **`docs/specs/dcr.md`** — short `## Audit Log` section between `## Admin API` and `## Future Works`, plus the matching TOC entry. It states that DCR lifecycle actions are audit logged, links to event.md for `oauth.client.registered`, and carries the two rules that are DCR-specific rather than event-specific: no token value is ever written to the audit log, and failed registrations produce no entry (with the `rate_limit.blocked` pointer). No payload shapes — those live in event.md. Cross-links added from the Registration Endpoint Response, IAT management, and New mutation sections.
- **`docs/specs/audit-log.md`** — correct `user: User!` to `user: User` in the provisional GraphQL sketch and say when it is null. The implementation has always been nullable (`pkg/admin/graphql/audit_log.go:452`); the four new user-less activity types make the discrepancy actively misleading.

## 8. Fixed Behavioral Decisions

- Four event types, not one generic `dcr.*` event. The three admin ones are named after their mutations because that is the invariant every one of the 56 existing `admin_api.mutation.*.executed` types follows, and the portal's `ADMIN_ACTIVITY_TYPES` bucket is derived from the `ADMIN_API` name prefix.
- The registration event is `oauth.client.registered`, not `dcr.client.registered`. Its `source` field carries `DCR` today and would carry `CIMD` when cimd.md ships, so a future CIMD emitter reuses the type instead of forcing a second near-identical activity type on every consumer.
- `ForHook() == false` for all four. Webhook delivery for administrative events is a broader product decision that no existing `admin_api.mutation.*` event has made, and `rate_limit.blocked` shows a `ForHook: false` event can still be a fully specified event.
- Only `oauth.client.registered` is documented in the specs; the three Admin API mutation events are not, matching all 56 existing `admin_api.mutation.*` events (§7).
- Payloads are purpose-built structs, never embedded `model.OAuthClient` / `model.OAuthInitialAccessToken` (§2). `oauth.client.registered` nests under `client` / `initial_access_token` to match event.md's documented-payload convention; the undocumented Admin API payloads stay flat.
- `initial_access_token` is a pointer and is omitted entirely — not emitted as null — when no IAT authorized the registration.
- No plaintext IAT, ever (§2.2), enforced by an e2e regression guard (§6.2 Case 3).
- Failed registrations produce no audit row (§1).
- `FillContext` sets `ctx.ClientID` for the two client-scoped events and leaves it empty for the two IAT events.
- `revokeInitialAccessToken` and `deleteDynamicClient` read before deleting so the audit row can describe what was destroyed; the extra `SELECT` is inside the same transaction and both are cold administrative paths.
- The registration handler dispatches inside its existing transaction and propagates a dispatch error, aborting the registration. Post-commit sink failures remain logged-and-swallowed by `event.Service`.
