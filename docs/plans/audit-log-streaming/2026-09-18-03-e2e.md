# Audit Log Streaming — Part 03: E2E

End-to-end coverage for [`docs/specs/audit-log-streaming.md`](../../specs/audit-log-streaming.md), on top of [part 01](./2026-09-18-01-config.md) and [part 02](./2026-09-18-02-runtime.md).

## Goal / scope

Prove, against a real Authgear deployment writing to a real TCP socket, that:

- an audit log entry is queued by the server, picked up by the background worker and delivered as a well-formed RFC 5424 message,
- a batch arrives in occurrence order,
- both framings work,
- the syslog options plumb through to the bytes on the wire,
- two streams each receive every entry,
- the feature config gate stops delivery at runtime,
- TLS with a project-supplied certificate authority works.

Parts 01 and 02 already cover the encoder, escaping, severity mapping, the queue scripts, the drop-oldest bound and mTLS in unit tests. This part covers the wire, the wiring and the producer-to-consumer hand-off — not the branch matrix.

The producer and the consumer live in two different processes, so this part is also the only place where the whole hand-off is exercised.

## 1. The recorder — `e2e/cmd/syslogserver/` (new)

A host process, built and started by `run.sh` alongside `e2e-smtp`, `e2e-proxy` and `e2e-cimdserver`. Not a container: it needs no image, and the auth server under test runs on the host, so loopback is the simplest reachable address.

`e2e/cmd/syslogserver/main.go`:

- **Plaintext listener** on `127.0.0.1:5140`.
- **TLS listener** on `127.0.0.1:6514`, using the fixtures from §2.
- **HTTP query API** on `127.0.0.1:5141`.

### 1.1 Frame decoding

One goroutine per accepted connection, reading with a `*bufio.Reader`. Framing is auto-detected per frame, so one recorder serves both kinds of stream:

- peek the next byte; if it is an ASCII digit, read the run of digits up to the following space, parse it as `n`, then `io.ReadFull` exactly `n` bytes — RFC 6587 octet counting;
- otherwise `ReadBytes('\n')` and strip the trailing LF — RFC 6587 non-transparent framing.

Record which branch fired as `framing` (`octet_counting` or `newline`) so a test can assert the sender used the framing it configured, rather than only that the message survived.

### 1.2 Message parsing

Each frame is parsed into a flat JSON object, so YAML assertions stay readable:

```json
{
  "framing": "newline",
  "port": 5140,
  "pri": 134,
  "facility": 16,
  "severity": 6,
  "version": 1,
  "timestamp": "2026-07-27T10:42:36Z",
  "hostname": "auth-7d9f8",
  "app_name": "authgear",
  "procid": "-",
  "msgid": "authgear-audit-log",
  "structured_data_id": "authgear",
  "structured_data": {
    "app_id": "...",
    "id": "...",
    "activity_type": "user.authenticated",
    "user_id": "...",
    "client_id": "...",
    "ip_address": "..."
  },
  "message": "{\"id\":\"...\",\"seq\":1,...}"
}
```

`pri` is split into `facility` and `severity` by the recorder (`facility = pri / 8`, `severity = pri % 8`) so tests assert on the two numbers rather than on the packed value. Structured-data parameter values are unescaped (`\\`, `\"`, `\]`) on the way in. `message` stays a string; a test that needs fields out of it asserts on the whole string or on `structured_data`, which carries the routable metadata precisely so a pipeline need not parse MSG.

A frame that does not parse is still recorded, with a `parse_error` field, so a malformed message fails a test loudly instead of looking like a missing message.

### 1.3 Query API

`GET /messages?app_id=<id>&port=<port>&min_count=<n>`

- `app_id` filters on `structured_data.app_id`. Every test gets a fresh random app ID from the runner, so this is what isolates concurrent tests sharing the one recorder.
- `port` filters by receiving listener, so a two-stream test can assert each destination separately.
- `min_count` makes the handler wait, polling internally at 50 ms up to 10 s, until at least `n` matching messages have arrived, then return. Delivery is asynchronous and batched, so without this every test would need a `sleep` step tuned by guesswork. With the 1 s e2e interval (§3.6) a 10 s ceiling leaves ample margin. `min_count=0` returns immediately, which is how the "nothing was delivered" assertions are written — those pair with a preceding `sleep` step, since no wait can prove a negative.

Response: `{"messages": [...]}`, ordered by arrival. The spec guarantees entries are delivered in the order they occurred, and a batch is written to one connection by one drainer, so arrival order is deterministic and needs no sorting — unlike `QueryHookServer`, which sorts by `seq` because non-blocking webhooks are delivered from fire-and-forget goroutines (`e2e/pkg/testrunner/cmd.go:317-321`). Preserving arrival order here is what makes §5.8 able to assert on it.

`GET /healthz` returns 200, for the `run.sh` readiness loop.

## 2. TLS fixtures — `e2e/ssl/` (new files)

The existing `e2e/ssl/ca.crt` is a CA certificate with no subjectAltName, so it cannot serve as a server certificate that Go will verify against `127.0.0.1`. The syslog recorder gets its own pair:

- `e2e/ssl/syslog-ca.crt` — the CA the test project trusts, referenced from `certificate_authority` in the test's secrets.
- `e2e/ssl/syslog-server.crt`, `e2e/ssl/syslog-server.key` — the recorder's TLS listener certificate, signed by that CA, with `subjectAltName = IP:127.0.0.1, DNS:localhost`.

Generated once and committed, with a validity long enough not to rot the suite (100 years). The generating commands go in `e2e/ssl/README.md` next to the files so they can be reissued:

```
openssl req -x509 -newkey rsa:2048 -nodes -keyout syslog-ca.key -out syslog-ca.crt \
  -days 36500 -subj "/CN=authgear-e2e-syslog-ca"

openssl req -newkey rsa:2048 -nodes -keyout syslog-server.key -out syslog-server.csr \
  -subj "/CN=authgear-e2e-syslog"

openssl x509 -req -in syslog-server.csr -CA syslog-ca.crt -CAkey syslog-ca.key \
  -CAcreateserial -out syslog-server.crt -days 36500 \
  -extfile <(printf "subjectAltName=IP:127.0.0.1,DNS:localhost")
```

`syslog-ca.key` is used only to issue the server certificate and is **not** committed — nothing in the suite needs it, and committing a CA key invites reuse.

No client certificate is issued: mTLS is covered by the unit tests in part 02 §11.5.

## 3. Runner support

### 3.1 New step action

`e2e/pkg/testrunner/models.go`:

```go
	StepActionSyslogServerQuery StepAction = "syslog_server_query"
```

Step fields, following the `smtp_log_query` shape (`models.go:645-648`):

```go
	// `action` == "syslog_server_query"
	SyslogServerPort     int          `json:"syslog_server_port"`
	SyslogServerMinCount int          `json:"syslog_server_min_count"`
	SyslogServerOutput   *QueryOutput `json:"syslog_server_output"`
```

`app_id` is not a step field — the runner always uses the test's own app ID, which is what makes isolation automatic rather than something each test has to remember.

Schema additions mirroring the `smtp_log_query` block (`models.go:466-473`): add `"syslog_server_query"` to the action enum, declare the three properties, and require `syslog_server_port` and `syslog_server_output` when the action is selected.

### 3.2 Query helper

`e2e/pkg/testrunner/cmd.go`, next to `QueryHookServer`:

```go
func (e *End2EndCmd) QuerySyslogServer(port int, minCount int) ([]interface{}, error)
```

`GET http://127.0.0.1:5141/messages` with `app_id=e.AppID`, `port` and `min_count`, decoding `{"messages": [...]}`. No sorting, for the reason in §1.3.

### 3.4 `run.sh` — the recorder

In `setup`, alongside the other helper binaries:

```
go build -o dist/e2e-syslogserver ./cmd/syslogserver
```

and a start block matching the `e2e-smtp` one, polling `http://127.0.0.1:5141/healthz` for a 200. In `teardown`, `kill_port 5140`, `kill_port 5141` and `kill_port 6514`.

### 3.5 `run.sh` — the background worker

Delivery runs in `authgear background`, which the e2e deployment does not currently start — `run.sh:35` starts only `authgear start`. Add a start block after it:

```
echo "[ ] Starting authgear background..."
authgear background > ./logs/authgear-background.log 2>&1 &
```

There is no HTTP endpoint to poll for readiness, so unlike the other helpers this one has no wait loop; the tests' own polling (§1.3) absorbs the startup delay. `teardown` kills it by name rather than by port, since it listens on nothing:

```
pkill -f "authgear background" || true
```

### 3.6 Delivery interval — `e2e/.env`

The default interval is one minute (part 02 §7.3). Waiting a minute per test is not acceptable, and `AUDIT_LOG_STREAMING_INTERVAL` exists precisely so it can be shortened:

```
# Audit log streaming delivers once a minute in production. The e2e suite
# asserts on delivered messages, so it runs the drain continuously instead.
AUDIT_LOG_STREAMING_INTERVAL=1s
```

`cmd/authgear/main.go:45` calls `godotenv.Load()`, so `e2e/.env` reaches both `authgear start` and `authgear background` with no further plumbing.

A 1s interval means the tests exercise the same code path as production with a different constant — they do not bypass the queue, and the producer-to-consumer hand-off is still fully covered.

## 4. Per-test secrets

Only the TLS test needs a secret, and `authgear.secrets.yaml` is not a per-test override in the runner — `createTempConfigSource` copies `e2e/var/` into a temp directory and merges only `authgear.yaml` and `authgear.features.yaml` (`e2e/cmd/e2e/pkg/configsource.go:68-140`).

The existing `extra_files_directory` mechanism covers it without a framework change. `CreateApp` runs `cp.Copy(extraFilesDir, configSourceDir)` *after* `var/` has been copied in, and `otiai10/copy` writes files with `os.Create` (truncating, `copy.go:108`) and merges directories by default (`copy.go:273`). So a file placed there replaces the shared one for that test alone.

The TLS test therefore carries:

```
e2e/tests/telemetry/audit_log_streaming/
  var/
    authgear.secrets.yaml
```

with `extra_files_directory: ./var` in the test case, matching the convention already used by `e2e/tests/hook/authentication.pre_initialize/var/deno/`.

Because the copy replaces the file rather than merging into it, that file is the shared `e2e/var/authgear.secrets.yaml` verbatim plus one appended item:

```yaml
- key: telemetry.audit_logs.streams.tls
  data:
  - stream_name: tls
    certificate_authority:
      pem: |
        -----BEGIN CERTIFICATE-----
        ... contents of e2e/ssl/syslog-ca.crt ...
        -----END CERTIFICATE-----
```

Two consequences to be aware of rather than surprised by:

- It must stay a **complete** secrets document. `SecretConfig.Validate` runs on every config load (`configsource/loader.go:49`) and the e2e base `authgear.yaml` declares an SSO provider and a confidential client, so `db`, `audit.db`, `redis`, `admin-api.auth`, `oauth`, `csrf`, `sso.oauth.client` and `oauth.client_secrets` are all required.
- It is a copy, so it drifts if someone adds a newly required secret to the shared file. That is a maintenance footnote, not a blocker: exactly one test carries the copy, and the failure mode is a loud load error in that test, not a silent wrong result. A comment at the top of the file says where it came from and why.

Only the TLS test needs this. Every other case below uses the shared secrets file unchanged.

## 5. Test cases — `e2e/tests/telemetry/audit_log_streaming/`

All cases drive a signup through the authflow, which produces `user.created` and `user.authenticated` audit entries, then query the recorder.

### 5.1 `newline.test.yaml`

`newline` framing, plaintext, default syslog options.

```yaml
name: Audit log streaming delivers an entry as RFC 5424 over TCP
authgear.yaml:
  override: |
    telemetry:
      audit_logs:
        streams:
        - name: collector
          type: syslog
          transport: tcp
          tcp:
            address: 127.0.0.1:5140
          syslog:
            format: rfc5424
            framing: newline
```

Asserts on the `user.created` message: `framing: newline`, `facility: 16`, `severity: 6`, `version: 1`, `msgid: authgear-audit-log`, `app_name: authgear`, `structured_data_id: authgear`, `procid: "-"`, `structured_data.app_id` equal to the test's app ID, `structured_data.activity_type: user.created`, and a non-empty `structured_data.id` and `message`.

Also asserts `hostname` equals `{{ .AppID }}.authgeare2e.localhost`. The e2e deployment's `public_origin` is `http://<app_id>.authgeare2e.localhost:4000` (`e2e/cmd/e2e/pkg/configsource.go` sets it per test), so this is the case that proves HOSTNAME comes from the project's public origin with the port stripped, rather than from the background worker's own hostname. It is templated because the app ID is generated per test.

### 5.2 `octet_counting.test.yaml`

Same, with `framing: octet_counting`. Asserts `framing: octet_counting` and that the message is intact — proving the length prefix the sender wrote matched the bytes that followed, since a wrong count desynchronises the stream and the recorder records a `parse_error`.

### 5.3 `syslog_options.test.yaml`

`facility: user`, `app_name: e2e-app`, `structured_data_id: authgear@12345`. Asserts `facility: 1` (the recorder's parsed numeric code for `user`), `severity: 6`, `pri: 14`, `app_name: e2e-app`, `structured_data_id: authgear@12345` — covering the `name@<private-enterprise-number>` form the spec's Caveats recommends for receivers that enforce RFC 5424 §6.3.2.

### 5.4 `two_streams.test.yaml`

Two streams, `newline` on `127.0.0.1:5140` and `octet_counting` on the same recorder, distinguished by `syslog_server_port`. Asserts both receive the same `structured_data.id`, proving every stream gets every entry and that the two are encoded independently.

### 5.5 `every_audit_entry.test.yaml`

Uses the existing `audit_query` step action alongside `syslog_server_query` in one test: performs a signup, queries the audit database, and asserts the streamed `structured_data.activity_type` values match the persisted `activity_type` values one for one. This is the direct test of the spec's "streamed if and only if it is persisted as an audit log", and it is the case that catches a regression where streaming drifts away from the sink.

### 5.6 `batch_order.test.yaml`

Performs a signup followed by a login, producing several entries in one or two drain windows, and asserts the delivered `structured_data.activity_type` sequence matches the order the entries occurred — `user.created` before `user.authenticated`.

This is the case that covers the property the queue design added: the spec no longer says "no order guarantee across processes", it says entries are delivered in the order they occurred, and a batch is written sequentially by one drainer. A regression that fans out per-entry sends or drains concurrently would show up here and nowhere else.

### 5.7 `feature_disabled.test.yaml`

```yaml
authgear.features.yaml:
  override: |
    telemetry:
      audit_logs:
        streaming:
          disabled: true
```

with a stream configured in `authgear.yaml`. Performs a signup, a `sleep` step, then `syslog_server_query` with `syslog_server_min_count: 0` asserting zero rows.

This is the **runtime** gate from part 02 §9, decision 9 — the save-time gate cannot be reached here, because the e2e runner writes the config source directly rather than through `UpdateResource`. That makes this case the only coverage of the downgrade behaviour outside unit tests, which is why it is worth its own file.

With the queue design the gate is enforced twice, at enqueue and at delivery, and this test exercises the enqueue side: nothing is ever queued. The delivery-side gate — a batch queued while enabled, drained after a downgrade — is covered by `runnable_test.go` in part 02 §11.4, because the e2e runner cannot change a project's feature config mid-test.

### 5.8 `tls.test.yaml`

```yaml
extra_files_directory: ./var
authgear.yaml:
  override: |
    telemetry:
      audit_logs:
        streams:
        - name: tls
          type: syslog
          transport: tcp
          tcp:
            address: 127.0.0.1:6514
            tls:
              enabled: true
          syslog:
            format: rfc5424
            framing: newline
```

with the secrets file from §4. Queries `syslog_server_port: 6514` and asserts the entry arrived — which can only happen if the TLS handshake completed and the recorder's certificate verified against the project's `certificate_authority`.

The stream is named `tls` to match the `stream_name` in the secret. A mismatch would not fail the load — part 01 §1.7 tolerates an orphan — it would silently fall back to the system trust store and the handshake would fail, so this case is also the one that catches the secret being looked up under the wrong name.

## 6. What is deliberately not covered here

- **mTLS** — unit tests, part 02 §11.5. It needs a client certificate fixture and a second listener configuration for one more branch of the same handshake.
- **Severity 4** (`email.error`, `sms.error`, `whatsapp.error`) — unit tests, part 02 §11.1. Provoking a real send failure in e2e would mean breaking the SMTP recorder, which would make the case about SMTP rather than about streaming.
- **The queue bound and drop-oldest** — unit tests, part 02 §11.3. Producing 10000 entries through the authflow to overflow the queue is not a reasonable e2e.
- **Dial failure and write timeout** — unit tests, part 02 §11.5. They need control over when the listener accepts and stalls, which the YAML runner does not have.
- **The redsync mutex across background replicas** — unit tests, part 02 §11.4. The e2e deployment runs one background worker.
- **SD parameter escaping** — unit tests, part 02 §11.1. Producing a `"` or `]` inside a user ID or client ID through the authflow is not reachable.
