# Audit Log Streaming, type datadog — Part 03: E2E

End-to-end coverage for `type: datadog`, on top of [part 01](./2026-09-23-01-datadog-config.md) and [part 02](./2026-09-23-02-datadog-runtime.md). The syslog suite it sits beside is [2026-09-18-03-e2e](./2026-09-18-03-e2e.md).

## Goal / scope

Prove, against a real Authgear deployment POSTing to a real HTTP server, that:

- an audit log entry is queued by the server, picked up by the background worker, and arrives at the destination as a Datadog log object,
- the log object carries the mapped attributes and the verbatim event,
- `datadog.service`, `datadog.source` and `datadog.tags` reach the wire,
- the request carries the `DD-API-KEY` from the secret, gzipped, as a JSON array,
- a batch arrives in occurrence order,
- a syslog stream and a datadog stream on the same project both receive every entry,
- the fetch address policy governs this path.

This part is the only place the whole chain runs in one piece: the intake answers `202` even to a malformed body, so an encoder defect is invisible to the sender. Something has to look at what arrived, and this is it.

## 1. The recorder — `e2e/cmd/hookserver`, extended

No new process, no new listener, no new TLS material. The suite's existing HTTP request recorder — the compose service `hook`, on `127.0.0.1:2626` — receives the intake requests, on a path the test owns:

```yaml
      http:
        endpoint: http://127.0.0.1:2626/[[.AppID]]/logs
```

That is how the hook tests already isolate themselves from each other while sharing one recorder (`tests/hook/ssrf_address_policy/blocked.test.yaml` uses `url: 'http://127.0.0.1:2626/[[.AppID]]/ssrf-blocked'`), and it works here because config overrides are templated with the test's app ID (`e2e/cmd/e2e/pkg/configsource.go`). Tests run in parallel (`e2e/pkg/testrunner/runner.go:55`), so this matters.

It is the right recorder because a Datadog intake is exactly what this server already models: an HTTP endpoint a project configures Authgear to POST to, like a webhook receiver or an SMS gateway. The alternative considered was extending `e2e/cmd/syslogserver` with an HTTPS listener of its own; it was rejected because it duplicates a recorder the suite already has, in a process whose name and shape are about a line protocol, for one property (a TLS handshake against a project-supplied CA) that part 02 §8.3 and §8.5 already cover in unit tests.

Three changes to `e2e/cmd/hookserver/main.go`. The first two are generic improvements, not datadog special cases — they are keyed on the request, not on the path:

### 1.1 Gzip and arrays

`POST /<path>` currently reads the body as a single JSON object and answers `400` otherwise. It gains:

- **gunzip** when `Content-Encoding: gzip`;
- **array explode**: when the decoded JSON is an array, append one record per element, instead of rejecting it.

A plain JSON object body behaves exactly as before, so no existing hook, SMS gateway or usage test changes.

### 1.2 The request envelope

Each record gains one reserved key describing the request it arrived in:

```json
{
  "…the log object's own fields…": "…",
  "__request": {
    "index": 0,
    "method": "POST",
    "content_type": "application/json",
    "content_encoding": "gzip",
    "headers": { "Dd-Api-Key": "e2e-datadog-api-key" }
  }
}
```

`index` is a per-recorder counter, so a chunking assertion can tell which request an element came from. Header names are canonicalised by `net/http`, hence `Dd-Api-Key`.

Adding a key to every record is safe for every existing test: object matching iterates the *expected* keys and ignores extra ones in the data (`e2e/pkg/testrunner/matcher.go:56`). It is recorded for all paths rather than only for intake-shaped requests, so that the record shape does not depend on the request shape.

### 1.3 The `202` response

The sender treats anything but `202` as a failed chunk (part 02 §4.5), and this server answers `200`. Without a change, every delivery would be recorded *and* logged as a failure, and the tests would pass while production behaviour was broken — the worst of both.

So, following the `sms-gateway/` precedent already in that handler, a request whose path ends in `/logs` is answered `202` with an empty body, which is what the real intake does.

### 1.4 `min_count`

`GET /<path>` returns immediately today, which is right for hooks: a hook is delivered during the flow step, so the request has already arrived by the time a test asks. Streaming is asynchronous behind the drain interval, so every assertion here would otherwise need a `sleep` tuned by guesswork.

`GET /<path>?min_count=<n>` makes the handler wait, polling internally at 50ms up to 10s, until at least `n` records exist at that path, then return whatever it has. `min_count=0`, and an absent parameter, return immediately — so the existing `QueryHookServer` behaviour is untouched.

## 2. TLS

None. The endpoint is plaintext `http` to loopback, which part 01 §1.6 accepts, as it does for a hook URL.

What that gives up is this part's only end-to-end exercise of the tls secret's `certificate_authority` on the http transport. It is covered in unit tests — `resolveHTTP` building the pool (part 02 §8.3) and the client verifying against it (§8.5) — and the same secret, parsed by the same code, is already exercised end to end by the syslog suite's `tls.test.yaml` over the tcp transport. That is the deliberate trade for not standing up a second TLS listener.

## 3. Runner support

### 3.1 `min_count` on the existing step

No new step action. `hook_server_query` gains one optional field, in `e2e/pkg/testrunner/models.go` beside `HookServerPath` (line 659):

```go
	// `action` == "hook_server_query"
	HookServerPath     string       `json:"hook_server_path"`
	HookServerMinCount int          `json:"hook_server_min_count"`
	HookServerOutput   *QueryOutput `json:"hook_server_output"`
```

Schema: declare `"hook_server_min_count": { "type": "integer" }` beside the existing two properties (line 312). It stays optional, so every existing test is unaffected.

### 3.2 Query helper

`e2e/pkg/testrunner/cmd.go`, `QueryHookServer` (line 333) gains the parameter:

```go
func (e *End2EndCmd) QueryHookServer(path string, minCount int) ([]interface{}, error)
```

It appends `?min_count=<n>` when `minCount > 0`. The existing `sortHookServerRowsBySeq` call stays: non-blocking webhooks are recorded out of order, and for datadog records the sort is a no-op, because it only applies when every row carries a `seq` — a Datadog log object has none at the top level. Delivered order is therefore preserved, which §5.3 depends on.

### 3.3 Step dispatch

`e2e/pkg/testrunner/testcase.go:410`, pass `step.HookServerMinCount` through. One line.

### 3.4 `run.sh` and the deployment

Nothing. The `hook` service is already built and started by docker compose, `authgear background` and `AUDIT_LOG_STREAMING_INTERVAL=1s` are already in place from the syslog part, and no port is added. This is the whole point of reusing the recorder.

## 4. Per-test secrets — `e2e/tests/telemetry/audit_log_streaming_datadog/var/authgear.secrets.yaml`

Every test here needs a secret, because part 01 §1.9 makes a `type: datadog` stream without an `api_key` a configuration that does not load. The existing `extra_files_directory` mechanism carries it, the same way the syslog TLS test does: the file replaces `e2e/var/authgear.secrets.yaml` for tests in this directory, so it must be a complete document — the shared file verbatim, plus one appended item.

```yaml
- key: telemetry.audit_logs.streams.datadog
  data:
  - stream_name: datadog
    api_key: "e2e-datadog-api-key"
  - stream_name: datadog2
    api_key: "e2e-datadog-api-key-2"
```

No tls item: nothing here uses TLS (§2).

Two consequences to know rather than discover:

- **One file, every stream name used in the directory.** An item whose `stream_name` matches no stream is tolerated (part 01 §5, decision 7), so each test declares only the streams it needs. Every test uses the stream name `datadog`; `datadog2` exists only for the two-stream case.
- **It is a copy of the shared secrets file** and drifts if a newly required secret is added there. Same maintenance footnote the syslog TLS test carries, same loud failure mode: a load error naming the missing key, in this directory only. The header comment says where it came from.

A distinct directory from `audit_log_streaming/` keeps the syslog tests on the shared secrets file.

## 5. Test cases — `e2e/tests/telemetry/audit_log_streaming_datadog/`

Each case drives the same email signup the syslog suite drives (`audit_log_streaming/batch_order.test.yaml`), which produces exactly two audited entries, in this order: `email.sent`, then `user.created`. Every stream is:

```yaml
    - name: datadog
      type: datadog
      transport: http
      http:
        endpoint: http://127.0.0.1:2626/[[.AppID]]/logs
```

`http.endpoint` rather than `datadog.site` in every case: the derived intake URL cannot be exercised without sending a project's audit logs to Datadog from CI. That derivation is unit-tested in part 02 §8.3, and the endpoint is what a project uses for an Agent or a worker anyway.

**On asserting rows.** `matchArray` (`e2e/pkg/testrunner/matcher.go:110-136`) is positional and length-exact: an element beyond the expected list is reported as `[[undefined]]`, and a missing one as a missing field. `["[[arrayof]]", {...}]` is the length-agnostic form, and `"[[ignore]]"` skips the element at one position but does not relax the length.

No runner change is needed, and none of these cases uses `[[arrayof]]`. The entry count per flow is deterministic — two — so every case pairs `hook_server_min_count: 2` with a two-element positional array, which is exactly what the syslog suite does and what makes an assertion on delivery *order* meaningful. Object matching inside each element stays subset-based, so a case names only the fields it is about.

Two properties this relies on, both already true: the two entries are delivered in one batch, so `min_count: 2` returns only once both have arrived; and `sortHookServerRowsBySeq` leaves these rows alone (§3.2), so index 0 is the entry that occurred first.

### 5.1 `delivery.test.yaml`

Defaults everywhere — no `datadog` object at all, proving the object is genuinely optional.

`hook_server_min_count: 2`, and a two-element array asserting `message: email.sent` at index 0 and, at index 1, the `user.created` record in full:

- `ddsource: authgear`, `service: authgear`, `message: user.created`, `status: info`.
- `hostname` equals `{{ .AppID }}.authgeare2e.localhost` — the project's `public_origin` host with the port stripped, not the worker's hostname.
- `evt.name: user.created`, `usr.id` non-empty, `network.client.ip` non-empty.
- `authgear.event.context.app_id` equals the test's app ID and `authgear.event.type` equals `user.created` — the verbatim event, which is the whole point of that attribute.
- `ddtags` equals `app_id:{{ .AppID }},activity_type:user.created`.
- `__request.headers.Dd-Api-Key` equals `e2e-datadog-api-key` and `__request.content_encoding` is `gzip` — the end-to-end proof that the secret was resolved and the body compressed, which no unit test can give, since the key's path from `authgear.secrets.yaml` through wire to the header only exists in a running deployment.

### 5.2 `datadog_options.test.yaml`

```yaml
      datadog:
        service: e2e-service
        source: e2e-source
        tags:
          env: e2e
          team: security
```

Asserts, on the `user.created` element, `service: e2e-service`, `ddsource: e2e-source`, and `ddtags` equal to `env:e2e,team:security,app_id:{{ .AppID }},activity_type:user.created` — configured pairs first in sorted key order, then the two appended from the event. The exact string, not a substring: ordering is a fixed decision (part 02 §9, decision 15) and a map-iteration regression would otherwise pass intermittently. The `email.sent` element at index 0 is asserted as `{ "message": "email.sent" }`, since a positional array has to account for it.

### 5.3 `batch_order.test.yaml`

`hook_server_min_count: 2` against `[{"message": "email.sent"}, {"message": "user.created"}]` — the positions are the assertion. It mirrors `audit_log_streaming/batch_order.test.yaml`, which pins the same two in the same order for the syslog type, and it is the case that catches a regression fanning out per-entry requests or reversing a chunk.

`__request.index` is **not** asserted here, on either element, even though the two usually do land in one drain tick and hence one request (both index `0`). Confirmed against a real run: whether they do is a race against the drain interval, not a guarantee — an entry enqueued just after a tick's drain has already started waits for the next tick, arriving as a separate, later request (index `1`). An earlier draft of this test asserted index `0` on both and was flaky for exactly that reason. The recorder still preserves arrival order across requests (§3.2), so the positional array assertion holds regardless of how many requests the two entries arrived in.

### 5.4 `every_audit_entry.test.yaml`

`audit_query` and `hook_server_query` in one test: perform the signup, read `activity_type` from `_audit_log` ordered by `created_at, id`, and assert the delivered `evt.name` values match it one for one — two rows, two records, same order. The direct test of "streamed if and only if persisted", for this type, and it mirrors `audit_log_streaming/every_audit_entry.test.yaml`. A third audited event appearing in a future flow change fails both suites' length assertion, which is the point: the two lists must stay identical.

### 5.5 `syslog_and_datadog.test.yaml`

Two streams on one project: the syslog recorder on `127.0.0.1:5140` (plaintext, `newline`) and the datadog stream. Uses `syslog_server_query` and `hook_server_query` in one test and asserts the same entry arrived at both, identified by `structured_data.id` on one side and `authgear.event.id` on the other.

This is UC3 across two types — independent encodings, independent transports, one batch — and it is the case that would catch the type switch (part 02 §1) sending both streams down one branch.

### 5.6 `fetch_address_policy.test.yaml`

```yaml
authgear.features.yaml:
  override: |
    http:
      insecure_fetch_address_allowed: false
```

with the same loopback endpoint as every other case. The features override is merged into `e2e/var/authgear.features.yaml` (`e2e/cmd/e2e/pkg/configsource.go:129`), so only this flag changes and `test_mode` is untouched.

Performs a signup, a `sleep` step, then `hook_server_query` with no `min_count` asserting zero rows.

The rest of the suite passes only because the e2e deployment sets `insecure_fetch_address_allowed: true`, which is exactly the self-hosted shape that flag exists for. This case proves the datadog transport is genuinely behind the policy rather than incidentally reaching loopback, and it is the e2e half of part 02 §8.5. It is also the one case where the recorder's own reachability is not what is being tested, so a false pass is impossible: the same endpoint delivers in every other case.

## 6. What is deliberately not covered here

- **`certificate_authority` on the http transport** — part 02 §8.3 and §8.5. The recorder terminates no TLS (§2). The same secret over the tcp transport is covered end to end by the syslog suite's `tls.test.yaml`.
- **Chunking and the size limits** — part 02 §8.2. Producing 1000 entries through the authflow to fill one chunk is not a reasonable e2e.
- **A non-202 response, and the `401`/`403` abort** — part 02 §8.2. The recorder would have to be told to misbehave per test, which the YAML runner cannot express.
- **The derived `https://http-intake.logs.<site>/api/v2/logs` URL** — part 02 §8.3. Exercising it means sending to Datadog.
- **A plaintext versus `https` endpoint** — nothing in the sender branches on the scheme (part 02 §9, decision 5); the scheme itself is part 01's config tests.
- **A missing `api_key`** — part 01 §4.5. It is a load failure, which the runner surfaces as an app that cannot be created, not as a test assertion.
- **The feature config gate** — already covered for syslog in `audit_log_streaming/feature_disabled.test.yaml`, and the gate is type-agnostic by construction: `Producer.Enqueue` returns before it knows a stream's type.
- **`status: warning`** — part 02 §8.1. It needs a real `email.error`, which means breaking the SMTP recorder, making the test about SMTP.
